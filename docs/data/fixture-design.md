# 모의 입력을 만든 이유와 한계

아래는 현재 보관 입력을 읽어 정리한 근거다. 실측 분포나 전문가가 보증한 운영 상수가 아니다.
기존 입력·156회/72회 결과를 수정하거나 최신 엔진으로 다시 계산한 기록도 아니다.

## 입력9종의 설계 목적

작업 수는 운송 작업 건수이며 독립 현장 사례 수가 아니다. 값 범위·해시는 [감사 결과](input-audit.json)로 재산출한다.

| 입력 | 작업/차량 | 구체적으로 확인할 것 | 인위적 단순화 |
|---|---:|---|---|
| `01_common` | 4/2 | 마감 단축, 출발 고정, 작업 조정, 준비 지연을 함께 설명 | 동일24000kg/DRY40·처리20분, 차고지·상차지·터미널만 사용 |
| `02_change_travel_tradeoff` | 1/2 | 변경을 줄이는 선택이 이동 부담을 늘릴 수 있음 | 처리0분·여유0분. 성능 우위를 만들기 위한 현장 표본이 아니라 절충을 드러내는 예제 |
| `03_keep_departure` | 1/1 | 가능한 원안 출발시각을 유지하는 목적 | 단일 작업·120분 반입 창 |
| `04_serve_before_change` | 2/2 | 변경 수보다 처리 수준을 먼저 비교 | 30분 창·DRY20/40 호환 조건의 인위적 차량 경쟁 |
| `05_fixed_reservation` | 2/1 | 미래 고정 예약을 유지하며 나머지만 조정 | 고정1개·처리/여유0분 |
| `20_jobs_4_vehicles` | 20/4 | 규모/시간 예산에 따른 계산·증명 한계 | 모든 작업24000kg/DRY40, 처리/여유0분, 단일180분 창 |
| `50_jobs_8_vehicles` | 50/8 | 제한시간·미증명 결과를 숨기지 않는 사례 | 같은 장소3개·단일 창·동일 장비/중량. 현실의 복잡한50건을 대표하지 않음 |
| `mixed_12` | 12/4 | 서로 다른 창·중량·장비·준비시각의 상호작용 | 중량18000~28000kg, 처리0/10/20분, 여유10분 |
| `mixed_fixed_12` | 12/4 | 혼합 조건에 출발·미래 고정 추가 | 고정2개(출발1개). 위치와 이동 구조는 여전히 단순 |

현 입력9종의 `data_mode`는 모두 `simulated`다. 작은/규모 입력의 이동 메타데이터는 `assumed`, 혼합 생성기는 같은 이동값까지 `simulated`로 다시 표시한다.
두 표기는 둘 다 실측이 아니라는 점을 유지한다. 출처 유형 숫자를 섞어 실제 관측 건수처럼 합산하지 않는다.

## 생성 규칙을 코드에서 확인할 수 있는 혼합2종

[기존 생성기](../../tools/build_engine_benchmarks.py)의 `build(fixed)`는 저장된20건 입력을 복사해 앞12작업과4차량을 사용한다.
시각 기준은2026-11-07 00:00 UTC다. 아래 수치는 경계·경쟁·다양성을 검증하기 위한 개발용 선택이며 운영 통계에서 추정한 값이 아니다.

- 시간창3개: 기준 후0~150,30~210,120~300분. 차량 근무 종료는330분.
- 준비시각: `(작업 인덱스 ×25) %190`분. 마지막 작업은320분으로 바꾸어 준비 지연 사례를 의도적으로 포함.
- 홀수 인덱스는 DRY20/18000kg, 짝수는 DRY40/24000 또는28000kg. 처리시간은 인덱스에 따라0/10/20분.
- 두 번째 차량은 DRY20·20000kg 제한, 네 번째는24000kg 제한을 주어 호환/중량 경쟁을 만든다.
- 원안 출발은 `20 + floor(인덱스/4) ×85`분. 실제 배차 담당자의 계획 품질을 재현한 규칙이 아니다.
- 고정형은 첫 작업을 이미 출발한 상태로, 여섯 번째를 미래 고정 예약으로 만든다. 원안·이유·차량 가용시각도 함께 맞춘다.
- 모든 사실 묶음의 출처를 `fixture:benchmark:<이름>`으로 다시 표시한다. 실수집으로 가장하지 않는다.

```sh
python tools/build_engine_benchmarks.py --output-dir local/mixed-rebuild
python tools/audit_data_evidence.py --inputs local/mixed-rebuild --output local/mixed-audit.json
```

신규 검사에서 생성 결과와 저장 입력 두 개를 JSON 객체로 대조했다. 기존 생성기와 그 결과는 변경하지 않았다.
앞선 작은/규모7종은 저장 Snapshot이 재현의 기준이다. 이번 작업에서 최초 생성 과정의 완전한 기록을 새로 복구했다고 주장하지 않는다.

## 왜 이런 값인가, 어디까지 설명할 수 있나

작은 입력은 손으로 제약을 확인하기 위해, 규모 입력은 같은 구조에서 작업 수와 시간 예산의 영향을 보기 위해 사용했다.
혼합 입력은 한 가지 장비·시간창만 있는 실험의 편향을 일부 드러내는 개발용 보완이다.
실제 이동·처리·준비 분포나 마감 변경 빈도를 추정한 것은 아니므로 현실성·수요·운송비 절감의 증거가 되지 않는다.

예를 들어20/50건 구조의 접근20+적재30+복귀10분과180분 마감은 차량당3건이라는 수작업 하한 설명을 가능하게 한다.
이 구조를 일반 항만 처리용량으로 해석하지 않는다. buffer0 역시 게이트 대기가 실제로 없다는 관측이 아니다.

## 개발용과 평가용의 구분

기존9종은 구현·성능 설정 선택에 사용한 개발/시연 입력이다. 독립적인 미사용 평가 세트로 표시하지 않는다.
기존228회는 두 엔진 버전의 모의 실행 합계이며 서로 다른 현장228사례가 아니다.
새 설정의 일반화 성능을 주장하려면 설정을 먼저 고정하고 별도 입력·예산·시드·실패/미증명 결과를 남겨야 한다.
이번 작업에서는 새 평가 실험이나 새 현장 효과 수치를 만들지 않았다.
