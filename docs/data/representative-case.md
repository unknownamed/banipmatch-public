# 대표4작업 · 데이터 담당 설명 순서

입력: [공통 Snapshot](../development/v0.1/예제%20데이터/01_snapshot.json).
같은 객체를 보관한 [실험01 입력](../experiments/engine-b0-b3/inputs/01_common.json)의 정규화 해시는
`1f6b7ea4e54e0e289d6aeda289e3edaf803c566e6657cd2101a1f618e8c76010`이다.
차량·항차·장소·시간·중량은 모두 모의이며, 이 해시는 실제 자료의 진위를 인증하지 않는다.

## 먼저 설명할 값

기준시각은2026-11-07 09:00 KST(`00:00Z`)다. 아래는 화면 설명용 KST이며 입력은 UTC다.

| 항목 | 값 | 의미·선택 이유 |
|---|---|---|
| 장소 | 가상 차고지D·상차지O·터미널HJNC | ID HJNC를 실제 현장 좌표로 오인하지 않음. latitude/longitude는 null |
| 차량 | T1/T2,30000kg,DRY20/40 | 두 차량 사이 조정 가능성을 작은 예제로 확인 |
| V1 창 | 08:00~12:00에서08:00~10:30으로 단축 | 확인된 변경에 대한 시나리오 내부 확정. 실제 터미널 공지 재현 아님 |
| V2 창 | 08:00~12:00 | 영향을 받지 않는 작업과의 교환 가능성을 확인 |
| 이동·처리 | D→O10분,O→HJNC30분,HJNC→D10분,처리20분 | 실측 이동·대기 데이터가 아닌 계산 가정 |
| 여유·변경 허용폭 | 여유10분,시각 변경 허용폭5분 | 관측 대기시간/현장 SLA가 아닌 명시적 비교 설정 |

| 작업 | 준비완료KST | 원안 | 설명할 판단 |
|---|---|---|---|
| J0 | 08:30 | T1,08:50출발→09:20반입→10:00복귀 | 이미 출발·고정. 원안 보존과 T1의10:00 가용을 확인 |
| J1 | 09:00 | T1,10:10출발→10:40반입 |10:40+여유10분은 새 마감10:30 초과. 다른 차량·순서 조정 후보 |
| J2 | 09:20 | T2,09:20출발→09:50반입 | V2 작업. J1과 조정해도 자체 마감·차량 접근/복귀를 지켜야 함 |
| J3 | 11:00 | T2,11:00출발→11:30반입 | 준비11:00+적재이동30+여유10=11:40>10:30. 순서만 바꿔 해결되지 않음 |

이 수작업 대조는 준비/마감 하한의 설명이다. 실행 결과의 전체 일정 검산이나 최적성 증명을 대신하지 않는다.
원안은 문제가 있는 계획도 그대로 입력할 수 있으므로 정상 입력 검증과 일정 실행 가능성을 구분한다.

## 입력 검사와 대표 오류 재현

```sh
python -m backend.data validate-json "docs/development/v0.1/예제 데이터/01_snapshot.json" --output local/case01-prepared.json --report local/case01-report.json
python -m backend.data validate-json "docs/development/v0.1/예제 데이터/07_snapshot_입력누락.json" --report local/case07-report.json
python -m backend.data validate-json "docs/development/v0.1/예제 데이터/08_snapshot_미확인변경.json" --report local/case08-report.json
```

- 01은 입력 검사 통과. J3을 임의로 고쳐 통과시키는 것이 아님.
- 07은 J1 준비시각 null로 `INPUT_MISSING`, 종료코드2. 준비시각0을 만들어 넣지 않음.
- 08은 미확인 반입시간으로 `WINDOW_UNCONFIRMED`, 종료코드2. 확정 변경으로 계산하지 않음.
- 미래 수신·관측/수신 역전·잘못된 참조·누락 이동은 [데이터 검사](../../tests/data)에서 재현.

## 전체 시연에서 맞출 연결

1. 같은 입력의 canonical 해시를 CLI·서버 등록·실계산 결과에서 대조한다.
2. 입력→B0~B3 계산→독립 일정 검사→원안/조정안·미처리·남는 위험 표시를 확인한다.
3. 같은 처리 수준인지 확인한 뒤 변경 수와 이동분·계산시간·해 상태를 함께 설명한다. 공통 예제에서 B3가 B2보다 항상 낫다고 말하지 않는다.
4. B0·설명용·검증 실패 결과의 내부 승인 차단과 이전 입력/계획 충돌을 확인한다.
5. 실제 내부 승인 성공을 보여주려면 서버 현재시각에 유효한 새 모의 입력이 필요하다. 과거 예제를 승인하려고 서버 시계·유효기간 검사만 끄지 않는다.

기존 [PR12·14 통합 검수](../team/handoffs/2026-11-08-pr12-pr14-integration.md)는 모든 시각을 함께 이동한 새 모의 입력으로 API·DB 승인을 확인했다.
이전 원본은 보존했으며 이 문서 자체가 새 브라우저 시연을 수행했다는 뜻은 아니다.

## AI·기존 도구와 팀 설계를 구분한 답변

Python CSV/JSON 처리는 표준 라이브러리, 구조 검사는 JSON Schema/jsonschema,
최적화 탐색은 엔진 담당의 OR-Tools 활용이다. AI는 구현·문서·검사 작성에 보조로 사용했다.
팀이 정한 업무 경계·필드 의미·고정 보존·시간/누락/출처 관계 검사·B0~B3 비교 목적과 회귀 사례를 설명한다.
도구 사용이나 검사 개수를 알고리즘 독창성·현장 효과로 바꾸지 않는다. 각 담당은 AI가 작성한 부분을 포함해 입력→판정→실패를 직접 설명할 수 있어야 한다.
