## 생성값의 의미

생성기 [build_evaluation_inputs.py](../../tools/build_evaluation_inputs.py)의 `build(profile, seed, count, vehicle_count)`를 기준으로 한다.

- 기준은2026-11-08 00:00 UTC. 차고지D·상차지O1/O2·터미널HJNC의 위치명은 가상이며 좌표는 null.
- 서로 다른 장소의 방향별 이동8~30분, 동일 장소0분을 명시한 완전 이동표. 부산 화물차 도로 실측이 아님.
- 준비0~60분, 처리5/10/15분, 계획 여유10분, 근무600분. readiness의 마지막 작업만 준비350분.
- DRY20 전용·20000kg 제한 차량과 일반 차량을 구성해 장비·중량 경쟁을 포함한다.
- 원안은 준비·이동·복귀를 반영해 순차 구성하며, 원래600분 근무를 넘으면 조용히 사례를 빼지 않고 생성 오류로 처리한다.
- 변경 전 원안에서 사건 후 입력을 복사하고 V1 창만 바꾼다. 작업·차량·이동·준비·고정·기준시각·원안은 그대로 유지한다.
- 사실 묶음은 `simulated`, 출처는 `synthetic:evaluation-v1:<사례ID>`, 관측시각은 null이다.

이 수치들은 실측 분포에서 추정한 것이 아니라 제약·절충·실패를 보이기 위한 선택이다.
준비350분을 사건 뒤 새로 알게 된 값처럼 설명하지 않고, 평가 입력에서 임의로 줄이지 않는다.

## 이번에 추가한 검사

[감사 도구](../../tools/audit_evaluation_data.py)와 [감사 결과](evaluation-input-audit.json)는 다음을 확인한다.

1. 프로토콜과 변경 전후 원본 바이트 SHA가 일치하는지. JSON 공백 변화도 원본 해시 변화로 검출.
2. 변경 전후 각각 현재 입력 검증기를 통과하는지. 실패 시 전/후 단계·원래 오류 코드·경로 기록.
3. 사례ID·작업/차량 수·모의 구분이 프로토콜과 일치하고 중복 사례가 없는지.
4. 바뀐 필드가 대상 창의 시작/마감뿐인지. 준비시각·이동·원안 등을 함께 고친 비교를 거절.
5. 사건의 이전 시작/마감이 보관한 변경 전 창과 일치하는지.
6. 현재 생성기 원본 SHA가 고정 기록과 일치하는지.

추가 회귀 검사에서는10사례 모두 생성기를 실행해 전후 객체가 보관한20개 입력과 같은지 확인했다.
솔버는 호출하지 않는다. 과거 결과의 독립 일정 검사·최적성 증명·승인 상태를 새로 바꾸지 않는다.

```sh
python tools/audit_evaluation_data.py --output local/evaluation-data-audit-new.json
python -m pytest tests/data/test_evaluation_data_audit.py -q
```

기존 출력은 덮어쓰지 않는다. 정상은 종료코드0, 해시/관계 등 검사 불일치는2, 프로토콜/파일 읽기·출력 실패는1이다.
프로토콜 경로 밖 파일은 읽지 않는다. 원본 또는 생성기가 변경되면 예전 SHA를 고쳐 통과시키지 말고 별도 평가 버전을 준비해야 한다.
보관 감사 결과는 현재 검사/감사 소스와 함께 재대조한다. 해시 일치는 외부 진위 인증이나 과거 동결 시점의 외부 증명이 아니다.
