# 반입맞춤 — 문제해결 보고서 본문 초안

작성일 2026-11-10. **검증된 기존 근거로 작성한 편집용 본문이며 최종 제출 PDF가 아니다.** 주제는 부산항 신항(진해) 수출 컨테이너 반입시간 변경 대응 배차 점검·조정이다. 황대겸 담당의 문제·방법·평가·한계 부분을 먼저 작성했다. 각 파트의 실제 연결·공개 계산·최종 배포 검수는 아직 인계 전이므로 완료 사실로 쓰지 않았다. [주장·근거표](evidence-index.md)와 [전체 작업](../team/completion-plan.md)을 함께 사용한다.

## 1. 해결하려는 문제

수출 컨테이너는 터미널이 허용하는 시간에 반입해야 한다. 반입 시작이나 마감이 바뀌면 기존 배차표에서 일부 작업이 너무 일찍 또는 늦게 도착할 수 있다. 이때 배차 전체를 처음부터 다시 만드는 것보다, 이미 출발했거나 변경할 수 없는 작업을 유지하면서 나머지 작업의 조정 가능성을 확인하는 기능을 검토했다.

프로젝트에서 확인한 HJNC 공개 공지는 반입마감 준수의 업무상 이유와 과거 반입 제한 일수의 변경 사례를 보여준다. 지연 반입 청구 공지는 지연 반입에 따른 재조작과 운영 차질을 설명한다. 2022년의 반입 제한 변경 공지는 운영 상황에 따라 시작 측 기준이 조정된 사례다. 다만 이 자료만으로 현재 변경 빈도, 운송사의 실제 손실, 담당자의 작업시간을 알 수는 없다. 과거 공지를 모든 항차의 현재 규칙으로 적용하지 않고, 담당자가 출처와 적용 항차를 확인한 변경값을 입력으로 받도록 했다. [공식 공지별 확인 범위](../team/operational-evidence.md)

주사용자는 HJNC 일반 수출 Dry 컨테이너 업무를 맡은 운송사 배차 담당자다. 시제품은 운송사 내부 작업의 차량·순서·출발시각 조정안을 제시한다. 최신 완성 범위는 미해결 조건 확인과 새 입력 재계산, 담당자가 확정한 변경의 대상자 전달·응답 확인까지다. 선석 배정, 터미널 예약 확정, 차량 모집·계약은 제외한다. 실제 기사 자료가 없어 최초 전달 검수는 기사 역할에 동의한 팀원의 휴대폰으로 진행하며, 이를 현장 운행 지시 실증으로 쓰지 않는다. [확정 범위와 구현 상태](../team/dispatcher-response-scope.md)

## 2. 기존 서비스와 검토 범위

공개 소개 자료에서는 TIGER FACE와 CONTAINUS TMS의 배차·운송관리, PortQM의 검역·서류 관리, PortWise의 선박·선석 운영 지원을 확인했다. 따라서 배차, 지도, 운송 추적, 일정 알림 자체를 새로운 기능으로 주장하지 않는다. 로그인 후 실제 기능과 알고리즘, 고객별 운영 방식은 시험하지 않았으므로 공개 소개에 없는 기능을 미지원이라고 단정하지도 않는다. [서비스별 출처와 비교](../team/service-comparison.md)

반입맞춤에서 검증하려는 내용은 확인된 반입시간 변경 뒤 기존 작업을 보호하면서 조정 대안을 설명할 수 있는지다. 처리 가능한 작업이 같더라도 작업 변경을 줄이면 이동이 늘어날 수 있다. 담당자가 두 부담을 함께 보고 판단하도록 원안, 마감순 대안, 이동 최소화 대안, 변경 최소화 대안을 비교한다. 기존 TMS의 배차 자료를 허용된 형태로 받아 쓰는 보조 도구라는 도입 방향을 생각하지만, 실제 TMS 연동 권한과 사용자 수요를 확보한 상태는 아니다.

## 3. 입력 자료와 계산의 경계

핵심 계산에는 작업·차량, 원안, 반입 허용시간과 확인된 변경, 화물 준비시각, 방향별 이동시간, 서비스·여유시간, 근무·복귀·고정 조건이 필요하다. 실제 운송사 배차표·차량 GPS·입출차 기록은 확보하지 못했으므로 해당 입력은 모의 자료로 구성했다. 현실의 발생 분포나 운송시간을 재현했다고 주장하지 않는다.

실제 자료는 제공자와 용도를 구분한다. HJNC 표본에서는 항차·반입 시작/마감·접안 예정 필드를 확인했다. 기상청에서는 해양관측과 특보 응답을 검증했다. AIS는 제한된 부산 수신 시험에서 선택 메시지를 받지 못했고, 별도의 지역 대조와 공급자 형식에 맞춘 합성 재생이 있다. 도로공사 응답은 단위·집계와 품질 문제가 남아 계산 채택을 보류했다. ORS는 개인 신청과 부산 방향별 표본 검증을 담당 작업으로 배정했다. 각각의 실응답 확인과 실제 웹앱 연결 완료는 다르다. [자료별 상태와 역할](../team/data-demo-sprint-2026-11-10.md)

실제 참고정보를 화면에 표시하는 것만으로 그 값이 배차 계산에 사용된 것은 아니다. 혼합 계산은 시간대·단위·권한·필수 필드와 저장·검증 경계가 확인된 경우에만 별도로 채택한다. 선박 ETA를 확정 반입마감으로 바꾸거나, 기상관측만으로 지연 원인과 시간을 확정하지 않는다. 실제 수집이 실패해도 모의값으로 자동 교체하지 않고 사용자가 선택한 모의 시연과 구분한다.

## 4. 조정 방법과 검증

B0는 원안을 유지한 위험 진단이다. B1은 마감순 삽입 기준선이며, B2와 B3는 OR-Tools를 이용한 제약 최적화다. 조정 방법은 미처리 수를 우선 다루고, B2는 이동 부담을, B3는 변경 부담을 비교하는 대안으로 사용한다. 목적의 단계별 증명 상태와 실제 일정의 유효성은 별도로 확인한다. [엔진 목적·제약](../../backend/engine/OPTIMIZATION.md)

출발·고정 작업의 차량·순서·시각은 보존한다. 새 시간창에서 고정 작업에 위험이 생겨도 작업을 삭제해 지표를 좋게 만들지 않는다. 준비시각이나 필요한 방향의 이동시간이 없으면 0분으로 채우지 않는다. 복귀가 미확인인 차량도 즉시 사용할 수 있다고 가정하지 않는다. 입력 부족, 시간 내 해 미발견, 증명된 불가능을 구분하고 확인한 수준의 사유를 보여준다.

변경 수는 차량 변경, 허용폭을 넘은 출발시각 변경, 순서 역전, 신규 배정의 합집합으로 센다. 미처리가 된 작업은 변경 수에서 빠질 수 있으므로 미처리 수를 먼저 확인한다. B2와 B3의 미처리 수가 같아도 처리 작업 ID가 다르면 동일 업무의 개선으로 합산하지 않는다. 엔진이 반환한 성공 표시만으로 승인하지 않고 API 담당의 독립 일정 검사와 현재 입력·계획 버전 검사를 거친다. 현재 로컬 승인은 내부 시연 계획에 대한 것이며 외부 예약·기사 통보가 아니다.

## 5. 모의 평가 결과

기존 동결 평가는 10개 합성 입력, 솔버 시드 2개, B0~B3로 총80회 계산했다. 작은8건 사례는 마감 단축·시작 지연·준비 지연·고정 위험을 두 생성 시드로 만들었고,20건·50건 규모 사례를 추가했다. 작은 사례의 예산은 방법당3초, 규모 사례는10초다. 입력·시드·소스 해시를 계산 전에 보존했으며 이 평가 결과에 맞춰 원본 조건을 바꾸지 않았다. [평가 설계·원시 기록](../experiments/engine-evaluation-2026-11-08/README.md)

80회는 서로 다른 현장80건을 의미하지 않는다. 같은 팀이 제약을 알고 생성한 합성 입력이며 작은 사례에는 공통 난수 구조가 있다. 원시 결과의 승인 불가 상태는 보존하고 별도 감사에서 조정 결과60개와 B0 원안20개를 확인했다.

|---|---:|---:|---:|---|
| 마감 단축8건·101 | 0/0 | 8→4 | 342→376 | 동일 |
| 시작 지연8건·101 | 0/0 | 8→3 | 342→410 | 동일 |

| 마감 단축50건·404 | 9/9 | 41→41 | 1860→1860 | 동일 |

B2/B3 전체20쌍은 미처리 수와 고정 위험이 같았지만 처리 작업까지 같은 것은14쌍이었다. 동일 작업 집합인 작은 사례12쌍에서는 변경이4~7건 줄어드는 대신 이동이12~82분 늘었다. 동일 집합의 나머지2쌍은50건 사례로 차이가 없었다. 이 사례에서 B3의 이점이나 전체 최적성을 확인하지 못했다. 다른 작업 집합6쌍은 별도로 해석한다. 전체 최적성 증명은 B2/B3 40회 중35회였으며 미증명 결과도 제외하지 않았다.

이 결과는 변경 부담과 이동 부담의 절충을 설명한다. 변경 최소화를 목적에 넣은 방법의 변경 수가 작다는 사실만으로 상용 TMS보다 우수하다고 결론내릴 수 없다. 변화량을 비용·업무시간·탄소 절감률로 바꾸려면 현장 계수와 검증이 추가로 필요하다.

## 6. 데이터 공백에 대한 행동

별도 작은 검수는4작업·2차량의9사례로 구성했다. 완전 입력4개에서 B0~B3 16회를 계산했고 조정안12개가 독립 검사를 통과했다. 불완전/미확정/미래근거5개는 솔버 호출 전에 차단했다. 기존80회 평가와 합쳐 현장 표본 수로 세지 않는다. [공백9사례·입력·원시 결과](../experiments/data-demo-2026-11-10/README.md)

준비시각을 가정으로 보완한 사례는 계산 가능 상태가 됐지만 미처리1건이 남았다. 고정 위험 사례도 출발 위험을 그대로 남겼다. 따라서 데이터가 추가되거나 순서를 조정하면 항상 모든 화물이 해결된다고 설명하지 않는다. 화면은 해결되지 않은 작업과 추가 확인할 자료를 함께 보여줘야 한다.

## 7. 실제 연결·공개 계산·배포 검수 — 인계 후 작성

현재 실제 연결·배포·휴대폰 전달 부분은 완료 사실이 없어 확정하지 않는다. 제출 전 각 담당의 검증을 대겸이 통합한다.

대응 안내 로직은 모의 입력의 B1 계산 결과를 독립 재검사한 뒤 이전·신규 차량별 변경 명세와 미해결 확인 안내를 생성했다. 고정 작업 J0를 유지하고, 재배정 J1/J2는 양쪽 차량에 표시하며 준비 지연 J3는 확인할 조건을 안내했다. 미처리를 운송 취소로 바꾸지 않고 원래 오류·근거를 보존한다. [입력·결과·명세·해시](../experiments/dispatch-response-2026-11-10/README.md)는 코드 동작의 증거이며 현재 서버 승인·실제 전송 권한의 증거가 아니다.

조건 편집→새 입력 재계산→담당자 확정→웹 푸시→수신자의 명시 확인/수행 가능·곤란 응답→담당자 상태를 완성 기준으로 삼았다. 이 흐름의 API/화면 연결과 실제 Android Chrome·iPhone 홈화면 수신 검수는 아직 남아 있다. 푸시 중계망 접수, 화면 열람, 사람의 확인, 운송 완료를 각각 구분하고 이 결과가 확보된 뒤에만 본문에 완료 사실을 추가한다.

- 민준: 공급자별 실제 응답일/범위·필드·권한·공백과 확정된 이유, 사용한 합성 예제·추가자료.
- 선효: 실제 읽기 응답/실패·한도 처리, 시연 세션별 저장/계산 분리, 입력/동시 계산/시간 상한, 오래된 결과·중복 적용·재시작 검사.
- 길웅: 실제/재생/모의 UI·지도, 세션/초기화·계산 제한과 오류 안내, PC/모바일/빠른 전환 검수.
- 대겸: 최종 main SHA·동일 입력/실행/계획 확인·통합 오류 보완, 직접 구성한 서버/URL·배포 버전, 팀원의 실제 URL 테스트와 수정·재확인 결과.

기존 정적 결과 탐색 화면은 보조로 남기며 새 계산이 가능한 배포본이라고 쓰지 않는다. 공개 시연은 개인정보 없는 모의 입력으로 제한하고, 실제 자료 공개는 제공자 권한이 확인된 범위만 사용한다. 서버·주소·실제 배포는 대겸이 직접 수행한다.

## 8. 도입 조건과 한계

운송사가 쓰려면 허용된 배차표와 확인된 반입시간, 준비·복귀·차량 조건을 현재 입력에 대응시켜야 한다. TMS의 내보내기 형식과 사용 허가, 담당자의 변경 허용 범위, 예외 절차와 입력 준비 비용을 확인해야 한다. 공개 시연용 세션 분리는 실제 회사의 권한관리·운영 수준을 검증한 것이 아니다.

현재 현장 배차·GPS, 실제 항차 변경 전후 쌍, 변경 대응의 빈도·시간·비용, 사용 의향은 확보하지 못했다. 기상과 AIS는 참고자료이며 지연 원인을 확정하는 모델이 아니다. 후속 협조로 실제 비식별 배차와 담당자 판단을 얻으면 제약의 적합성, 입력 준비 부담, 제시한 절충의 가치부터 검증할 수 있다. 허용 범위 안에서 그 검증을 거친 뒤 운영 적용을 논의한다.

## 최종 편집 체크

본문·표지·참고문헌 전체를20쪽 이내로 편집한다. 원본 공고는 자유양식 보고서20페이지 이내와 데이터/코드 등 일체의11/13 14시 이메일 제출을 요구한다. 보고서PDF·코드ZIP은 팀 제출 방식이며 배포 URL만으로 코드를 대신하지 않는다. 이번 작업에서 발표자료는 만들지 않는다. 수치/그림은 원시 기록·실행 버전을 연결하고, 새 배포에서 실제 확인한 사실만7절에 넣는다. 아직 배포하지 못했으면 미배포 사실을 적고 과거 로컬 기록을 배포 검수처럼 사용하지 않는다.
