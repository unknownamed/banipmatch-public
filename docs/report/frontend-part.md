# 화면·사용성 파트 본문·근거 인계 · 최길웅

기준 main `740a2fb`, 작업 브랜치 `codex/choigilung-dispatch-response`(PR #64), 2026-11-11. 전체 보고서 20쪽 편집을 맡은 대겸에게 전달하는 화면 파트 원고다. 최종 보고서가 아니며, 아래의 확인 범위와 미완료 표시를 유지해 [본문 초안](report-draft.md) 7절에 반영한다.

## 본문에 사용할 설명

화면의 주사용자는 운송사 배차 담당자다. 반입시간이 바뀐 뒤 담당자가 한 화면에서 차례로 확인하도록 구성했다. 순서는 변경 근거, 원안과 조정안의 차이, 남는 문제, 조건 보완, 내부 확정, 대상자 전달, 응답 상태다. 별도의 채팅·연락처 관리·기사 관리 기능은 만들지 않았다. 기사 쪽은 변경 내용을 보고 응답만 하는 작은 수신자 화면 하나로 제한했다.

**변경 근거를 먼저 보여준다.** 화면 첫 부분은 어느 항차·터미널의 반입 허용시간이 어떻게 바뀌었는지와 그 출처·확정 여부·수신시각이다. 선박 접안예정(ETA)이나 트럭 방문예약 시간이 아니라 항차별 반입 시작·마감이라는 점을 문구로 밝힌다. 자료가 모의이면 "자료: 모의"를 함께 표시한다.

**조정안의 이득과 남는 위험을 같이 보여준다.** 미처리·제약 위반·고정 작업 위험·변경 작업·이동 부담을 원안과 조정안으로 나란히 비교한다. 차량별 시간축에는 마감 초과, 조정안 변경, 고정 작업을 구분해 표시한다. 다음은 성공처럼 보이지 않게 따로 드러낸다.
- 미처리로 남은 작업
- 이미 출발한 작업의 위험
- 설명용 예시 결과: 승인 대상이 아니라는 배너를 띄우고 승인 버튼을 막는다.

**승인 전에 위험을 직접 확인하게 한다.** 승인은 세 단계(위험 확인 → 승인 요청 → 내부 계획 확정)다. 미처리·고정 위험 작업을 체크해야 승인 버튼이 켜진다. 승인은 운송사 내부 계획 확정일 뿐이며 터미널 예약 변경·TMS 반영·기사 통보가 아니라고 화면에 적었다.

**조건을 보완해 다시 계산할 수 있다.** 담당자가 확인한 상차 준비시각과 차량 가용·근무 시각만 고칠 수 있다. 고정·출발 작업과 반입 마감, 이동시간은 입력 칸 자체가 없다. 고칠 때는 다음을 지킨다.
- 수정 이유를 반드시 받는다.
- 확인된 조건과 가정 시험을 고르게 한다. 가정 시험 결과는 비교만 할 수 있고 승인할 수 없다.
- 원래 입력과 결과는 그대로 남긴다. 새 입력은 이전과 같은 방법·계산 시간·seed로 다시 계산해 전후를 비교한다.
- 전후 비교에는 서버가 붙인 해석 한계를 그대로 보여준다. 예를 들어 기준시각이 함께 바뀌었으면 "조건만의 효과로 볼 수 없다"고 표시한다. 개선율로 바꿔 쓰지 않는다.
- 시각은 기기 설정과 관계없이 24시간제 한국 시각으로 입력받는다. 표시 형식과 입력 형식을 맞추기 위해서다.
- 외부에서 확보가 확인된 차량을 추가할 수 있다. 모든 사양을 직접 입력해야 하고, 다른 차량 값으로 채우지 않는다. 시작 위치는 이동시간이 이미 있는 위치만 고른다. 차량을 구해 주는 기능이 아니다.

**확정한 변경만, 명시적으로 전달한다.** 내부 승인 뒤에만 차량별 변경 명세와 담당자가 확인할 사항이 나온다.
- 재배정된 작업은 이전·새 차량 양쪽에 표시한다. 미처리로 바뀐 작업은 "운송 취소 아님"으로 표시한다.
- 시험 수신자 초대는 운영자가 허가한 시연 세션에서만, 동의 확인 뒤에 만든다.
- 전달은 확인 상자를 체크한 뒤에만 보낸다. 같은 승인을 두 번 보내지 않는다.
- 상태는 두 갈래로 따로 보여준다. 전달 쪽은 대기·중계망 접수·실패·결과 불명·미연결·이전 계획이다. 사람 쪽은 열람·확인함·수행 가능·수행 곤란이다. 중계망 접수는 읽음이 아니고, 수행 가능은 운송 완료가 아니다. 결과 불명은 중복 수신을 막기 위해 자동으로 다시 보내지 않는다.

**수신자 화면은 휴대폰 한 손 사용을 기준으로 했다.**
- 잠금 화면 알림에는 일반 문구만 나온다. 일정·차량·항차는 화면을 연 뒤 권한을 확인하고 보여준다.
- 내 차량의 변경만 보이고, 상대 차량 쪽 일정은 "상세 비공개"로 가린다.
- 응답은 확인함·수행 가능·수행 곤란 버튼으로 직접 고른다. 화면을 연 것만으로 확인으로 처리하지 않는다. 수행 곤란은 담당자의 후속 확인이 되며 자동 재배차하지 않는다.
- 이후 계획이 바뀐 알림은 상세를 가리고 응답을 받지 않는다.
- 이름·전화번호를 받지 않는다. 초대 비밀은 주소의 `#` 뒤에서 읽은 즉시 지운다.
- iPhone은 홈 화면에 추가한 웹앱에서만 웹 푸시를 받을 수 있고, Safari와 쿠키가 따로 저장된다. 그래서 Safari에서는 초대를 받지 않고, 홈 화면 추가 후 앱 안에 붙여넣도록 안내한다.

화면 코드는 AI 보조로 작성했다. 화면 담당은 각 표시가 어떤 응답 필드에서 오는지, 어떤 경우에 버튼을 막는지, 오류마다 무엇을 안내하는지를 설명할 수 있어야 한다. 화면은 계산 결과의 원인을 새로 만들지 않고 서버 응답의 지표·문제 코드·한계 문구만 표시한다.

## 그림 후보 (최종 배포본 화면으로 다시 캡처)

2026-11-12 임시 시연 서버(`fe983bd`)에서 찍은 그림과 설명·근거 ID는 [figures/frontend](figures/frontend/README.md)에 있다. 최종 배포본에서 바뀐 부분이 있으면 다시 찍는다.

1. 결과 화면 상단: 변경 근거 카드(이전·새 반입 허용시간, 확정 여부·출처)와 계산 상태 표
2. 원안·조정안 비교와 차량별 시간축(마감 초과·조정안 변경·고정 표시)
3. 승인 3단계와 위험 확인 체크
4. 조건 보완 카드와 전후 비교(가정 시험이면 "승인 불가" 표시)
5. 변경 전달·응답 카드의 대상별 상태표
6. 휴대폰 수신자 화면: 변경 내용과 응답 버튼. 모의 링크 `/recipient?demo=1`로 캡처하면 그림 설명에 "모의 화면"을 반드시 적는다

그림에는 실행 ID·커밋·자료 구분(모의)을 함께 적는다. 로컬 개발 화면을 배포본 검수처럼 쓰지 않는다.
