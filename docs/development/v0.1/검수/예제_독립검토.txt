개발 초안 v0.1 — 엔진 입력·설명용 결과 독립 검수
검토 대상: contracts.schema.json, 01_snapshot.json, 04_results_설명용.json, 예제_기대결과.json. 추가로 Run 정의, 실행 요청/상태 및 생성 스크립트의 해시 방식을 확인했다.
원본·계약·예제는 수정하지 않았다. 이 검수는 엔진 실행이나 최적성 증명이 아니다.

결론
B0/B3의 시간, 가용시각, 복귀, 변경 지표에 계산 오류를 찾지 못했다. 계약에는 아래 실행 재현 메타데이터 보완이 필요하다.

1. 시간 재계산(모두 KST)
공통: 적재 이동 30분, 여유 10분, 터미널 처리 20분, 복귀 10분. 따라서 복귀는 게이트 도착 후 40분이다. 별도 PowerShell 계산으로 모든 배정의 도착·복귀값 일치를 확인했다.
B0 J0: 08:50 → 09:20 → 10:00, 고정 작업 유지.
B0 J1: 10:10 → 10:40 → 11:20. 여유 포함 10:50으로 새 마감 10:30을 초과한다.
B0 J2: 09:20 → 09:50 → 10:30. 마감 12:00을 지킨다.
B0 J3: 11:00 → 11:30 → 12:10. 준비시각부터 가장 일찍 출발해도 여유 포함 11:40으로 새 마감 10:30을 지킬 수 없다.
B3 J0: 원안과 동일.
B3 J1/T2: 09:10 → 09:40 → 10:20. T2의 09:00 가용시각 + 접근 10분을 지킨다.
B3 J2/T1: 10:10 → 10:40 → 11:20. J0 종료 후 T1의 10:00 가용시각 + 접근 10분을 지킨다.
모든 배정 작업은 준비·중량·장비·18:00 근무 종료를 만족한다. 변경 전 마감 12:00 기준으로 원안 J1/J3도 시간창에 들어간다.

2. 지표 재검산
B0: 이동가능 작업 3개 중 정상 1, 위반 2. 미처리 0, 고정 위험 0. 공차 접근 10+적재 이동30+복귀10의 합 50분×3=150분.
B3: 이동가능 작업 정상 2, 위반 0, J3 미처리 1, 고정 위험 0. 이동 50분×2=100분.
차량 변경 J1/J2. 출발시각 변화 J1 -60분, J2 +50분으로 허용폭 5분을 넘는다. 순서 변경은 원안·대안 모두 같은 차량에 남은 작업쌍의 역전이 없으므로 0. 합집합은 J1/J2 두 건이며 J3 삭제를 변경 건수에 섞지 않는다.
J0는 시간·차량·순서 그대로 유지됐다. 전체 작업은 배정과 미처리에 중복 없이 보존됐다.

3. 필수 계약 보완 제안
현재 Run은 요청의 seed/time_limit_seconds를 돌려주거나 보존하는 필드가 없고, 엔진/솔버/모델 버전·동일 초기해나 설정의 식별값도 없다. MethodResult는 objective_proven 한 값뿐이므로 사전식 단계별 목적값·해 상태·하한/상한을 저장할 수 없다. additionalProperties:false여서 문서가 요구하는 단계별 기록을 덧붙일 수도 없다.
최소한 Run에 불변 실행 설정(seed, 전체 시간 예산, 엔진/모델/솔버 버전, 설정/초기해 식별값)을 두고, B2/B3 결과에 objective_stages(단계명, 목적값, 상태, 경계 또는 미제공 사유)를 추가하는 편이 좋다. 별도 실행 메타데이터 계약으로 분리해도 되지만 run_id와 연결·보존 규칙을 명시해야 한다.
시간 예산은 방법별 전체 예산이며 여러 사전식 단계가 공유한다는 뜻을 필드 설명에 남기면 프론트·엔진 구현 해석 차이를 줄일 수 있다. 동일 시드만으로 시간 제한 병렬 솔버 결과가 반드시 같다고 보장하면 안 된다.

4. 의미 검증으로 유지할 조건
출발한 작업은 frozen=false가 잘못 들어와도 이동 금지. 고정 복귀와 차량 가용시각이 충돌하거나 복귀가 미확정이면 새 배정 차단. 같은 차량 점유 중복, 미래 고정 예약, 누락 이동시간을 0으로 채우는 오류는 독립 검사기가 막아야 한다. JSON Schema의 구조 검사만으로 이 조건을 통과했다고 표현하지 않는다.

5. 설명용 결과 표기
B3 FEASIBLE, result_origin=illustrative_fixture, objective_proven=false, approval_eligible=false는 적절하다. elapsed_ms=0과 동일 시작/종료 시각은 수작업 예제 자리값이며 실제 속도 측정으로 사용하지 않아야 한다. 기대결과 파일의 고지는 이 구분을 명확히 한다. 이 예제는 유일 대안이나 최적 대안임을 주장하지 않는다.

추가 검수 — 2026-11-07, 계약 보완 및 원안 미처리 이월
앞선 3번의 필수 보완은 최신 contracts.schema.json에서 반영된 것을 확인했다. Run.config의 seed/time_limit_seconds와 nullable error, MethodResult의 engine_version/solver_version/objective_stages/validation_status가 추가됐다. 단계별 objective/status/value/best_bound를 담을 수 있다. 설명용 결과는 fixture-only-0.1.0, solver_version=null, objective_stages=[], validation_status=not_run으로 실제 솔버 계산·독립 검사 완료와 구분된다. 따라서 기존 3번은 미반영 지적으로 남지 않는다. 별도 자동 구조 검증은 주 담당자가 수행한다.

원안 미처리 이월 모델도 타당하다. baseline_assignments와 baseline_unassigned_job_ids의 서로소 합집합이 jobs여야 하며, 출발·고정 작업은 배정에 있어야 한다. 모든 작업이 원안 미처리인 경우를 위해 baseline_assignments의 minItems:1이 제거된 것을 확인했다. 신규 배정은 newly_assigned_job_ids로 보존하고, 양쪽 배정 유지 작업의 차량/시각/순서 변경과 합쳐 changed_job_ids를 정의한다. unassigned_count는 결과의 전체 미처리 수다. 원래 배정됐으나 이번에 빠진 작업만 뜻하지 않는다. 해당 신규 미처리 집합은 원안 배정−결과 배정으로 구별한다.

현재 fixture의 원안 미처리와 신규 배정 목록은 비어 있으므로 기존 시간·지표 검산 결론은 변하지 않는다. 향후 인수 사례에 원안 미처리 작업의 신규 배정, 전부 미처리인 원안, 승인 후 미처리 포함 계획을 새 입력으로 넘기는 흐름을 포함하면 좋다. 신규 배정을 변경 집합에 포함하는 것은 v0.1의 명시적 정의이며 기존 배정 변경 세 유형과 구분하여 표시한다.

tmp/team_draft/engine_pages.json에 원안 분할·B0 미처리 보존·신규 배정 합집합·전체 미처리 의미·실행 메타데이터 보존을 반영했다. 3쪽 한글 글자 수는 각각 768/768/767자로 요청 범위에 들어간다. 계약과 예제 원본은 수정하지 않았다.
