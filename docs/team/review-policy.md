# 리뷰와 병합 기준

적용일: 2026-11-07. 팀 논의 뒤 사용자가 적용을 요청한 현재 기준입니다. 이전의 모든 PR에 작성자 외 승인 필수·수정 후 재승인 대기 규칙을 대체합니다.

## 어떤 변경에 리뷰를 요청하나요?

| 변경 | 처리 |
|---|---|
| 문구·디자인·작은 오류 수정, 담당 영역 내부의 작은 변경 | 작성자가 변경에 맞는 검사를 하고 PR에 결과를 남긴 뒤 병합 |
| 큰 기능 추가, 다른 파트와 연결되는 변경 | 영향을 받는 담당자에게 1회 검토 요청 |
| 공통 API·DB·필드 의미 변경, 고정 작업 보존·승인 처리 등 중요한 공통 동작 변경 | 관련 담당자 검토. 두 파트의 판단이 모두 필요할 때만 2명 요청 |

파일 수만으로 크기를 판단하지 않습니다. 한 줄 수정도 저장 데이터·고정 작업·승인 조건을 바꾸면 중요한 변경입니다. 문서의 오타처럼 경로만 겹치는 변경에는 해당 경로 담당자 전원을 호출하지 않습니다. 담당과 코드 경로는 [역할표](roles.md)를 따릅니다.

PR에는 `리뷰 불필요 — 이유` 또는 `리뷰 필요 — 대상·이유`를 짧게 남깁니다. GitHub의 공식 Approve 버튼만을 검토 증거로 요구하지 않습니다. 관련자가 남긴 실질적인 검토 댓글도 1회 검토로 인정합니다. AI 자체 검사는 사람의 검토가 이루어진 것처럼 기록하지 않습니다.

## 한 번 검토한 뒤의 흐름

1. 리뷰어는 치명적 오류, 계약 불일치, 다른 파트와의 연결 문제를 우선 확인합니다. 취향이나 무관한 개선 때문에 병합을 지연시키지 않습니다.
2. 작성자는 지적된 문제를 고치고 필요한 검사와 회귀 확인을 수행합니다.
3. PR에 지적별 수정 내용·커밋·검사 결과를 남깁니다. 사소한 개선을 후속 작업으로 남기면 이유와 담당을 함께 적습니다.
4. 알려진 중요한 문제를 해결하고 관련 검사·CI가 통과하면 **재검토 요청과 추가 Approve를 기다리지 않고 병합**합니다. 수정할 때마다 리뷰어를 다시 호출하지 않습니다.

고정 작업 손실·임의 변경, 데이터 손상, 잘못된 승인, 현재 요청과 다른 결과 표시, 필수 계약 위반, 비밀값 노출 같은 이미 확인된 문제나 관련 검사 실패는 해결 전 병합하지 않습니다. '통합할 때 검사한다'는 이유로 알려진 중요한 문제를 넘기지 않습니다. 확인하지 못한 범위는 완료로 적지 않습니다.

원래 피드백 수정과 무관한 큰 기능·공통 계약 변경이 추가되면 후속 PR로 분리해 해당 변경에 필요한 검토만 받습니다. 기존 수정에 대한 반복 재검토를 요구하기 위한 예외로 사용하지 않습니다.

## AI가 작업할 때

- 작업 브랜치와 PR은 유지합니다. 작은 변경도 diff·검사·변경 이유를 남기며, 모든 구현을 main에 직접 쓰는 규칙으로 해석하지 않습니다. 사용자가 명시한 직접 반영은 그 범위를 따릅니다.
- 시작할 때 최신 main, 역할·현재 상태와 이 기준을 읽습니다. 오래된 PR 본문·인계·배포 PDF의 승인 대기 문구보다 현재 기준을 우선합니다.
- 관련자에게 필요한 1회만 요청합니다. 이미 검토한 사람에게 수정 커밋마다 재요청하거나, 이유 없이 전체 팀을 리뷰어로 추가하지 않습니다.
- 이미 받은 지적은 수정·검사 근거로 처리합니다. 검사 실패를 숨기거나 테스트를 약화하지 않습니다. 사람의 승인 리뷰를 대신 작성하거나, 미해결 지적을 해결됐다고 처리하지 않습니다.
- 사용자는 병합 과정에서 발견한 오류를 병합 담당 AI가 직접 수정·검사해 main에 반영하도록 허용했습니다. 담당자가 다르다는 이유로 수정 요청만 돌려보내지 않습니다. PR 브랜치 또는 별도 수정 브랜치에서 변경과 검사를 남기고 병합하며, 이미 병합된 작은 수정은 허용된 범위에서 main에 반영할 수 있습니다. 무관한 새 기능·공통 계약 변경으로 확대하지 않습니다.
- 병합 직전에 최신 PR head와 CI, 새로 들어온 중요한 지적, 충돌 여부를 확인합니다. 검사한 뒤 head가 바뀌었다면 바뀐 부분에 필요한 검사만 수행합니다. 같은 검사를 이유 없이 반복하지 않습니다.
- GitHub의 실제 병합 제한은 우회하지 않습니다. 필수 검사 실패나 충돌은 해결하고, 설정 변경이 필요하면 실제 차단 원인을 기록합니다. 강제 푸시·검사 무력화·리뷰 기록 삭제로 통과시키지 않습니다.

`.github/CODEOWNERS`의 자동 요청 패턴은 비활성화했습니다. 담당 정보는 역할표에서 확인하고, 필요할 때 PR에서 관련자만 선택합니다. 브랜치 보호나 필수 검사 설정을 해제하는 변경은 하지 않았습니다.

## 통합 검수

파트 연결 시에는 입력 등록 → 계산 → 원안/조정안 표시 → 오류·미처리 설명 → 내부 승인 흐름을 정밀 검사합니다. 이전 입력 결과의 승인 차단, 고정 작업 보존, 누락·실패·충돌도 포함합니다. 각 담당자가 자기 연결 문제를 함께 고치며, 통합 담당자 한 명에게 모두 넘기지 않습니다.

이것은 개발 PR의 검토 절차입니다. 제품 안의 계산 결과에 필요한 독립 일정 검사와 내부 계획 승인 조건은 그대로 유지합니다.
