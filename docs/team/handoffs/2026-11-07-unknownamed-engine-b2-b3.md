# 황대겸 · B2/B3 최적화와 모의 비교

최신 main `5b32d77`에서 시작했습니다. 기존 `solve(snapshot, method, config) → MethodResult` 및 배포 계약 v0.1은 유지했습니다. 핵심 계산 기능 추가이므로 API·독립 검증 담당 안선효에게 관련자 1회 리뷰를 요청하는 범위입니다.

## 구현

- `backend/engine/optimization.py`: 차량별 선택 경로, 선택 작업 시간·장비·중량 제약, 출발 기록 보존·미래 고정 예약, 정수 순서 슬롯, B2 미처리→이동/B3 미처리→변경→이동.
- 상위 목적을 증명한 뒤에만 다음 단계로 진행합니다. B1 초기안·모형 구성·모든 단계는 동일 총 예산을 사용하고, 시간 종료 시 가장 좋은 유효 후보를 유지합니다.
- B3의 변경 목적은 차량/허용폭 초과 시각/같은 차량 쌍의 역전 참여/신규 배정의 합집합입니다. 반환 지표와 모형 목적값이 다르면 오류로 중단합니다.
- `solver.py`의 B1 구성을 공통 내부 함수로 추출해 초기안에서도 같은 로직을 사용합니다. B0/B1의 기존 계약과 검사는 유지합니다. CLI 기본 비교는 B0~B3입니다.
- 솔버 의존성은 `backend/engine/requirements.txt`, CI 개발 설치는 `requirements-dev.txt`에 추가했습니다. 서버가 엔진을 연결할 때 이 의존성도 설치해야 합니다.

- [7개 모의 입력 비교](../../experiments/engine-b0-b3/README.md): 작은 사례에서 B3의 변경 감소와 이동 증가, 차량 재배정으로 처리 증가, 개선 없는 동률을 함께 확인했습니다. 20/50작업·3초는 FEASIBLE이며 최적성 미증명입니다.

## 선효에게 요청하는 검토

함수 계약이 같아 API 엔드포인트는 수정하지 않았습니다. 다음 연결에서 아래 부분을 한 번 확인해 주세요.

1. 고정 배정·차량·순서 정수·시각을 유지하는지, 선택 작업의 시간/복귀/근무 조건이 독립 검사에서도 맞는지.
2. `solution_status`, `objective_proven`, `objective_stages`와 실제 실행 상태를 구분하는지. 유효한 B1 초기안이 있으면 솔버 단계 UNKNOWN에서도 최상위 FEASIBLE일 수 있습니다.
3. `validation_status=not_run`, `approval_eligible=false`는 그대로입니다. 엔진의 최적성 증명을 독립 일정 검증이나 내부 승인으로 대체하면 안 됩니다.

리뷰 지적을 수정하고 관련 검사·CI가 통과하면 최신 팀 규칙대로 반복 재요청·추가 승인 대기 없이 병합합니다. AI의 보조 검토를 팀원의 검토로 기록하지 않습니다.

## 후속 작업과 한계

API 실행 연결·독립 검사·승인 저장·전체 화면 연결은 선효/길웅과 후속 통합합니다. 대겸은 시간 예산·입력 규모별 실험과 계산 병목 개선을 이어갑니다. 희소 경로는 보수적 입력 부족이며 고정 순서 정수 제한도 유지합니다. 모형 최적성은 이 계약의 범위입니다. 키 발급·외부 연락·실제 운송 자료·배포는 이번 작업에 포함하지 않았습니다.
