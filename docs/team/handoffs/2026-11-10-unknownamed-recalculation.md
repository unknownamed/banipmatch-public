## API에서 가져다 쓸 함수

`backend.engine.recalculation.validate_condition_revision(before, after, reason=...)`는 기존 Snapshot 두 개를 받아 수정된 조건·원래/새 근거·추가 차량과 이동경로·입력 해시를 반환한다. 준비시각과 기존 차량의 가용/근무 시각, 조건이 완비된 차량 추가를 지원한다. 새 위치/방향별 경로는 추가 차량의 상차지 접근에 필요한 것만 허용한다. 기존 작업/차량 삭제, 장비·용량 변경, 고정 작업 수정, 반입시간·원안·정책·기존 이동시간 변경은 거절한다. 누락값을 만들어 채우지 않는다.

`compare_recalculation(before, before_results, after, after_results, method="B1", reason=...)`는 기존 Results 응답 두 개를 입력 해시·실행ID·같은 계획/버전으로 묶고 각각 독립 일정검사를 다시 수행한다. B1/B2/B3 중 같은 방법을 비교한다. 입력/결과를 수정하거나 솔버·DB·네트워크를 호출하지 않는다.

- 새로 배정된 작업, 새 미처리, 계속 미처리, 정확한 일정 변경, 추가/해소/잔여 고정 위험을 구분한다.
- 각 결과의 상태·증명 수준·문제/근거·지표·설정을 보존한다. 처리 작업 집합·고정 위험·계산 설정/버전/예산·기준시각이 다르면 효율 비교 값은 `None`이고 한계를 반환한다. 원시 지표 차이는 그대로 남긴다. 설정이 둘 다 비어 있어도 동일 예산이라고 하지 않는다.
- 처음에 준비/가용시각 누락으로 입력검사가 차단된 경우 `before_results=None`을 허용한다. 이전 오류를 반환하고 미처리0건·효율 개선율을 만들어내지 않는다. 원래 계산 가능한 입력이면 이전 결과가 반드시 필요하다.
- 새 근거를 받을 때 `as_of`는 앞으로 갈 수 있다. 시간 경과 영향을 별도 표시하고 순수 조건 효과로 비교하지 않는다. 시간을 과거로 돌리거나 입력 유효기간을 연장할 수 없으며 새 시각에서도 의미 검사를 통과해야 한다.
- 반환값은 서버 내부 비교 자료다. 새로운 HTTP/DB 계약을 확정한 것이 아니며 `delivery_authorized=false`다. 승인·현재 버전/만료·세션 권한·수신자/전달 판단은 기존 서버 경계를 거쳐야 한다.

## 연결 위치와 남은 작업

선효 #54에서 수정 이유/근거와 새 입력·실행을 저장한 뒤 위 함수를 호출할 수 있다. 같은 base plan을 유지한 조건 보완 비교이며, 실제 계획이 이미 승인·변경됐으면 새 기준을 확보해야 한다. 프론트 응답으로 노출할 필드/오류는 길웅과 관련자1회 계약 검토로 맞춘다. 이 모듈이 HTTP 접근 권한이나 외부 확인의 진위를 검증하는 것은 아니다.

대겸의 이번 완료는 재계산 비교 **구현과 회귀**다. 실제 조건 편집 화면→새 입력→계산→비교·푸시/응답 연결은 #54/#55 인계 후 통합한다. 예전 오프라인 변경 명세와 동결80회 원본은 보존했다.

검사: `python -m pytest -q tests/engine/test_recalculation.py tests/test_dispatch_response.py tests/engine/test_metrics.py`. 준비 보완만으로 미해결이 남는 경우, 차량 추가로 해결, 새 미처리·고정 위험, 시간/설정 차이, 입력 부족, 방향별 경로 누락, 해시/버전·일정/지표 변조를 실제 B1 계산으로 대조한다. 네트워크·서버 실행·실제 수신 시험은 하지 않는다.
