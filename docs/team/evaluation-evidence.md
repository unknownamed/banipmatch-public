# 심사 항목별 주장과 증거 준비

기준일: 2026-11-08. 사용자가 제공한 심사표를 현재 구현·실험에 연결하는 팀 작업 기준입니다. 공식 최신 공고를 새로 확인한 문서가 아니며 점수 예측이나 수상 보장이 아닙니다. 제출 전 공식 공고의 항목·분량·제출 시각을 다시 확인합니다.

주제는 **부산항 신항(진해) 수출 컨테이너의 확인된 반입시간 변경에 대응하는 운송사 배차 점검·조정**으로 유지합니다. 코드·공통 v0.1 계약·담당을 바꾸거나 새 기능을 추가하는 지시가 아닙니다. 각 담당은 기존 범위에서 아래 증거를 준비합니다.

## 실험 수치의 사용 기준

- 기존 156회와 후속 72회는 **228회 모의 실행**입니다. 현장 운송 228건·서로 다른 현장 사례 228개·현재 버전의 재검증 228회를 뜻하지 않습니다. 엔진 0.2.1과 0.2.2의 기록을 분리하고 최신 0.2.3 구현과도 구분합니다.
- B3의 변경 최소화 목적에서 변경 수가 줄었다는 사실만으로 일반 성능 우위나 현장 효율을 주장하지 않습니다. 먼저 미처리 수·작업 구성이 비교 가능한지 확인하고, 변경 수와 함께 이동 부담의 증가/감소, 조정 작업 위반, 고정 잔여 위험, 계산시간·시간 예산·해 상태를 제시합니다. 처리 수준이 다르면 같은 효율 개선률로 합치지 않습니다.
- 모의 20건 B3·3초에서 변경 10→2, 같은 10초 호출 중앙값 5.21→2.42초는 해당 입력·장비·버전의 결과입니다. 50건 B3·10초의 변경 23은 최소라고 증명되지 않았고, 3초의 전체 최적성도 미증명입니다. 일부 성공만 골라 일반화하지 않습니다.
- 기존 실험의 `validation_status=not_run`, `approval_eligible=false`는 보존합니다. PR12의 독립 검사 구현이나 후속 병합이 과거 실행을 소급 검증했다는 뜻은 아닙니다. 엔진의 자체 진단·목적값 대조와 API의 독립 일정 검사를 구분합니다.
- 새로운 모형·탐색 설정을 평가한다면 **개발용 입력/예산으로 선택한 설정을 먼저 고정**하고, 선택에 사용하지 않은 별도 평가 입력으로 비교합니다. 입력 출처·특성, 시드·반복·예산, 실패/시간 초과·미증명, 소스 버전과 원본 결과를 남깁니다. 소규모 독립 전수열거 또는 엔진과 별도의 일정 검산으로 제약·지표도 확인합니다. 기존 228회가 이러한 분리 평가를 충족했다고 주장하지 않으며, 이번 문서가 새 실험 실행을 지시하는 것은 아닙니다.
- 현장 시간·비용 환산은 실제로 확인한 계수·단위·적용 범위가 있을 때만 별도 시나리오로 계산합니다. 솔버 실행시간 단축을 배차 담당자의 업무시간 절감으로 바꾸지 않습니다.

## 우선순위와 권한

먼저 차별성과 정량 효과의 주장마다 기존 근거·부족한 증거를 연결합니다. 이어 같은 사례의 데이터·계산·화면·검사 결과를 담당별로 맞춥니다. 실제 연결 완료는 반영된 버전과 확인 결과로 상태 문서를 갱신하고, 미병합 PR이나 예정 작업을 완료로 쓰지 않습니다. 새로운 지도·추적·알림 기능을 늘리는 계획으로 바꾸지 않습니다.

API 가입·신청·새 외부 메일·실자료 사용 권한 확보는 이번 문서 작업으로 재개하지 않습니다. 기존 보류·개별 승인 범위를 유지하며 [API 준비 현황](api-access-status.md)과 최신 직접 사용자 지시를 먼저 확인합니다. 공식 최신 공고를 재조회한 문서는 아닙니다. 작업 중 별도 사용자 지시로 당시 열린 PR12·14만 대겸 계정에서 AI 보조 검토·병합했으며, 선효가 직접 검토한 것으로 기록하지 않습니다.

| 반입시간과 선박 ETA는 어떻게 다르고, 이 제약은 어디서 왔는가? | 데이터 담당의 출처·적용 터미널·확인시각, [업무 의미와 비교](service-comparison.md). 현장 규칙과 실험 가정을 구분 |
| 기존 배차 서비스가 있는데 왜 필요한가? | 엔진·화면 담당의 동일 사례 비교. 미확인 경쟁 기능을 미지원으로 쓰지 않고 남는 불편을 가설로 제시 |
| 변경 최소화를 목적에 넣었으니 변경 수가 적은 것은 당연하지 않은가? | 같은 처리 수준의 이동 손해·시간·미처리·잔여 위험까지 제시. 변경량을 실제 업무 부담으로 해석할 근거는 별도로 확보 |
| 모의 데이터가 현실을 얼마나 반영하는가? | 데이터·엔진 담당의 생성 규칙·범위·가정·실패 사례와 개발/평가 분리. 실제 배차 표본 미확보와 일반화 한계 명시 |
| OR-Tools와 AI가 한 일, 팀이 설계한 일은 각각 무엇인가? | 솔버 사용과 목적·제약·고정 보호·입력/결과 검사·비교 설계를 구분. 각 담당이 자기 코드의 입력→판정→오류를 재현·설명 |
| 해를 못 찾거나 잘못된 결과가 나오면 어떻게 하는가? | [엔진 모형](../../backend/engine/OPTIMIZATION.md), API 독립 검사와 승인 차단. 시간 초과·입력 부족·증명된 불가능을 구분 |
| 운송사가 실제로 쓰려면 무엇이 더 필요한가? | 입력 권한·필드 변환·운영 인증·사용자 격리·비용·수동 대안. 로컬 내부 승인을 실제 예약 변경으로 설명하지 않음 |

핵심 흐름은 짧고 쉽게 설명하고, 질의응답에는 해당 원자료·제약·실험 결과·코드 경로로 근거를 제시합니다. 모르는 현장 사실은 미확인이라고 답하며, 심사위원의 소속을 추측해 설명 수준이나 결론을 바꾸지 않습니다.
