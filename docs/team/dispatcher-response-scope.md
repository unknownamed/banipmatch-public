# 반입맞춤 완성 범위 — 담당자의 대응을 끝까지 돕기

2026-11-10 사용자 최종 요구를 반영한 설계 v6의 후속 결정이다. 대화 중 검토한 ‘푸시는 선택/후순위’는 이 문서로 대체한다. **아래 포함 기능은 모두 완성 범위다.** 개발 순서와 완료 범위를 혼동하지 않는다. 아직 구현·실기기 검증하지 않은 것을 완료라고 하지 않는다.

## 서비스와 채택 이유

반입맞춤은 **부산항 신항(진해)의 확인된 수출 반입시간 변경에 대응해, 운송사 배차 담당자가 기존 배차의 문제를 찾고 실행 가능한 대응을 결정·전달·확인하도록 돕는 서비스**다. 대상은 HJNC 일반 수출 Dry이며 항만 전체 관제나 모든 운송업무 관리가 아니다.

조정안을 제시하는 데서 끝내면 담당자는 미처리 원인 확인·조건 보완·누구에게 무엇을 전달할지 다시 정리해야 한다. 따라서 조건 재검토, 차량별 변경 명세, 전달·응답까지 이어지는 최소 흐름을 완성한다. 다만 이것은 설계 판단이며 업체 실사로 효과·선호 채널을 입증한 상태는 아니다. 기존 TMS를 보조한다는 방향과 양립하며 기존 TMS에 자동 반영하는 기능은 아직 확보하지 않았다.

웹 푸시는 그 흐름에서 **확정 변경을 대상자에게 알리는 구현 방식**으로 채택한다. 연락 기능을 만들기 위해 별도 채팅·연락처 관리 제품을 만들지 않는다. 실제 기사 자료가 없으므로 최초 검수는 모의 배차+기사 역할 팀원의 실제 휴대폰으로 한다. 실제 휴대폰 수신은 실증할 수 있지만 현장 도입·실차량 운행 실증과는 다르다.

## 확정 완료 기능

| 번호 | 사용자가 실제로 할 수 있어야 하는 일 | 구현·검수 기준 |
|---|---|---|
| R1 문제 확인 | 변경 항차/반입시간·출처와 너무 이른/늦은 작업·누락·고정 위험 확인 | ETA를 마감 변경으로 쓰지 않음. 실제/참고/가정/모의와 조회 실패 구분 |
| R2 조정 비교 | 순서·시간·가용 차량 재배정 대안과 원안 비교 | 고정/출발 보존, 준비/이동/장비/용량/근무 조건, 미처리·위반·변경·이동 부담과 증명 수준 |
| R3 다음 대응 확인 | 미해결 작업에 대해 확인할 조건·담당 역할·근거 보기 | 오류 코드에 근거한 확인 안내. 해결 보장·추측한 원인 금지. SEARCH_LIMIT는 불가능 아님 |
| R4 확인된 조건으로 재계산 | 준비시각·차량 가용/근무 조건 보완 또는 조건이 완비된 차량 추가 후 새 결과 비교 | 원본·이전 결과 보존, 새 입력/버전·수정 이유·출처. 가정 시험은 가정 표시. 실제 차량을 구해주는 기능 아님 |
| R5 확정과 변경 명세 | 담당자가 위험/미처리를 검토·확정하고 누구의 어떤 일정이 바뀌는지 확인 | 최신 입력·실행·계획 재검사. 재배정은 이전·신규 차량 모두, 미처리 전환은 자동 운송 취소 아님 |
| R6 대상 전달 | 최초 연결/동의한 수신자에게 확정 변경의 웹 푸시 전달 | 외부 업체 가입 없는 VAPID 방식. 대상 미연결·거절·실패·불명을 표시. 승인 전/오래된 계획/다른 세션/중복 차단 |
| R7 응답 확인 | 기사 역할 수신자가 변경 내용을 열고 확인·수행 가능/곤란을 답하며 담당자가 확인 | 푸시 접수≠읽음≠확인≠수행 가능≠운송 완료. 곤란 응답은 후속 확인 대상으로 돌아가며 자동 재배차하지 않음 |
| R8 기록·보고서·배포 | 같은 입력/계획/전달 버전의 근거를 보고서와 제출 코드에 연결 | 사용자별 접근 분리, 실제 HTTPS 주소·기기 검수, 기존 F01~F12·20쪽 보고서/코드·데이터 제출 유지 |

R4는 무제한 편집기가 아니다. 우선 `ready_at`, 차량 `available_at`/`shift_end_at`와 차량 추가를 지원한다. 추가 차량의 장비·용량·가용/근무·위치·방향별 이동시간 등 필요한 값이 없으면 계산 차단/부족 항목 안내를 한다. 고정 상태 해제, 마감 연장, 누락 이동시간 0 보충으로 결과를 좋게 만들지 않는다. 실제 추가 차량 계약이나 확보는 담당자가 외부에서 확인해야 한다.

## 범위에서 제외하는 것

- 차량/기사 자동 모집·계약, 협력사 대차 확정, 터미널 예약·마감·선적 변경 승인, 관세/서류 처리 대행.
- 실제 트럭 GPS·기업 배차표가 없는 상태의 실시간 운행 관제나 지연 원인 확정.
- 전화 자동 발신, 전화번호 필수 등록, 별도 채팅·카카오 단톡방 생성, SMS/알림톡 업체 가입·결제.
- ‘추가 차량 확보됨’, ‘예약 변경됨’, ‘실기사 확인함’ 등 실제로 수행하지 않은 행동을 모의 성공으로 대체.

확인할 곳과 필요한 조건을 안내하는 것은 R3, 외부 기관의 허가·계약을 우리 서비스가 대신 실행하는 것은 제외 범위다. 현장에 필요한 일이 곧 우리 서비스가 직접 실행할 수 있는 기능인 것은 아니다.

### 지금 대겸이 준비한 인계물

`tools/dispatch_response.py`는 실계산 조정안의 일정 재검사 후 차량별 차이와 확인할 사항을 만든다. `bind_archived_approval`은 저장된 입력·실행·계획·승인의 해시/버전을 대조하지만 현재 서버 권한을 대신하지 않는다. 출력에 `delivery_authorized=false`를 유지한다. **R3/R5의 로직 인계이며 R6 전송 구현이 아니다.** [인계/실행법](handoffs/2026-11-10-unknownamed-dispatch-response.md)을 읽는다.

## 전달·응답 계약에서 반드시 맞출 것

공개 계산/세션 경계와 함께 선효·길웅이 새 계약을 정한다. 아래는 요구사항이고 구현 완료된 API 목록이 아니다.

- 차량ID·기사/시험 수신자ID·푸시 구독은 별개다. 최초 연결로 실제 수신자를 확인하고 운행/계획 범위로 묶는다. 수신자 미연결을 성공으로 집계하지 않는다.
- 서버는 승인된 최신 계획/입력 버전의 변화만 전송 대상으로 만들고, 고정 위험·미처리를 누락하지 않는다. 알림은 일반 문구만, 상세는 권한 확인된 화면에서 보여준다.
- 전송 대기/중계망 접수/실패/결과 불명과 사람의 확인/수행 가능/곤란 응답을 구분한다. 읽기만 했다고 확인으로 간주하지 않는다. 무응답 시 재촉 메시지를 자동 발송하지 않고 담당자 확인 대상으로 표시한다.
- 발송 후 계산 결과가 바뀌면 예전 알림을 ‘이전 계획’으로 표시한다. 이전 버전에 응답하거나 다른 사람의 알림을 열지 못하게 한다. 통보 전 버전 재검사와 수신 시 최신성 검사를 둘 다 한다.
- 타임아웃/서버 재시작 후 중복 발송 가능성을 제어한다. 기사 응답과 수정 이력은 입력/계획 버전으로 연결한다. 명시적으로 재계산·재확정하기 전 새 운송 지시로 자동 승격하지 않는다.
- 초대 토큰·구독 endpoint/키·VAPID private key는 인증 자료다. Git/로그/보고서/공개 번들에 넣지 않는다. 만료·해제·수신자 격리·보관/삭제·요청량 제한과 endpoint 검증을 구현한다.
- 현재 로컬 공통 토큰·loopback 제한을 그냥 풀지 않는다. 공개 세션 분리와 별도로 시험 발송 권한을 제한한다. 공개 방문자가 남의 수신자/임의 번호로 전송할 수 없어야 한다.

## 웹 푸시 준비와 완료 증거

외부 문자업체·Firebase·사업자 등록은 필수가 아니다. 자체 VAPID 키와 HTTPS 서버·Service Worker·수신자의 최초 방문/허용은 필요하다. 건당 문자 발송비는 없지만 서버/통신 운영비는 별도이며 브라우저/OS 푸시 중계망을 사용한다. iPhone은 지원 OS의 홈화면 웹앱 조건을 확인한다. 지원하지 않는 환경·권한 거절·설정 해제도 설명하고 숨기지 않는다.

완료 증거는 실제 배포 커밋과 URL, 단말/OS/브라우저, 수신 동의, 승인 계획 버전, 전송 상태, 휴대폰 표시, 변경 화면, 수신자 명시 응답, 담당자 상태의 왕복 기록이다. 최소 Android Chrome과 iPhone 홈화면 환경을 대상으로 하고 미검증 환경은 미검증으로 남긴다. 별도 설치형 채팅앱은 만들지 않는다.

보고서 기한은 기능을 완료로 둔갑시키는 근거가 아니다. 기한까지 남은 기능은 미구현/미검증으로 적고 작업 이슈를 열어 둔다. 완성 범위를 조용히 축소하거나 화면 알림으로 실제 푸시 완료를 대체하지 않는다.

## 근거와 확인 한계

- [체인포털 기사 매뉴얼](https://www.chainportal.co.kr/manual/download?filename=ChainPortal_APP_Manual.pdf): 운송오더 알림·예약/출발 확인 흐름. 과거 화면 예시이며 현재 전체 운송사의 업무/선호를 실사한 자료 아님.
- [컨테인어스 TMS](https://www.containus.kr/서비스-containus-tms/): 배차·협력 운송사 정보 공유·오더/터미널 정보. 우리 서비스의 우위/현장 도입 증거는 아님.
- [HJNC 업무 메뉴](https://www.hjnc.co.kr/esvc/board/notice): 미반입/Booking/COPINO 등 확인 기능. 열람 가능한 메뉴를 쓰기 API·예외 반입 승인 권한으로 해석하지 않음.
- [표준 Web Push](https://webkit.org/blog/12945/meet-web-push/), [iOS/iPadOS 조건](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Python pywebpush](https://github.com/web-push-libs/pywebpush): 기술적 가능성. 우리 단말 실수신 검증은 별도.

공식 자료 확인일 2026-11-10. 운송사의 실제 배차표·기사 연락망·기업 시스템 접근 권한은 미확보다. 따라서 시연은 명시적 모의 배차와 지정 팀원 수신자로 진행한다.
