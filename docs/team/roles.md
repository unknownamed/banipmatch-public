## 01 · 최길웅 — 프론트·화면

**완성할 것:** 배차 담당자가 변경 근거, 원안과 조정안, 미처리·고정 작업의 위험, 계산 상태를 한 화면에서 확인하는 웹 화면입니다. API 요청·응답을 연결하고 입력 오류·조회 실패·승인 충돌도 표시합니다.

- 첫 작업: 공통 예제의 J0 고정, J1/J2 조정, J3 미처리 이유를 설명용 응답으로 표시합니다. 설명용 결과임을 화면에 표시하고 승인하지 못하게 합니다.
- 계산 대기·실행·완료·실패와 결과의 해 상태를 구분합니다. 계산 중에도 원안과 근거는 확인할 수 있어야 합니다.
- API 응답에 없는 값이나 원인을 화면에서 만들어내지 않습니다. 늦게 도착한 이전 시나리오 응답이 현재 화면을 덮지 않게 합니다.
- 외부 항만 API 수집, 배차 계산, DB 저장을 프론트에서 구현하지 않습니다. 지도·움직이는 차량은 핵심 흐름이 연결된 뒤 검토합니다.
- **서비스 비교 반영:** 변경 사건→영향 작업→원안/조정안→미해결·잔여 위험을 우선 보여줍니다. 선박 ETA·확인된 반입시간·외부 예약 상태를 혼동하지 않고, 내부 승인 버튼을 예약 확정·기사 전송으로 표시하지 않습니다.
- **API 사전 준비:** 카카오맵 팀 앱·무료 적용 여부·로컬 개발 도메인·멤버 권한을 준비하고 [진행표](api-access-status.md)의 AP-04를 갱신합니다. 지도 앱과 자동차 길찾기 권한을 구분하고 AP-08의 앱 설정은 선효와 맞춥니다. 키 발급 자체를 지도 기능 구현 완료로 표시하지 않습니다.
- 안선효와 요청·오류·조회 상태를 맞추고, 황대겸과 비교 지표·미해결 설명의 표시를 확인합니다.
- 인계물: 실행 방법, 주요 화면·상태별 확인 기록, API 연결 목록, 미구현 사항.

## 02 · 심민준 — 데이터 처리·입력 검증

**완성할 것:** CSV·JSON과 이용이 허용된 외부 응답을 내부 공통 규격으로 바꾸고, 다른 파트가 사용할 입력의 의미와 출처를 검사하는 데이터 모듈입니다.

- 첫 작업: 기존 모의 CSV·JSON을 읽고 ID·참조·시간대·단위·누락·중복을 검사한 뒤, 정상 입력과 행별 오류를 돌려줍니다. 외부 API 승인 없이 기존 예제로 시작합니다.
- 첫 구현은 [데이터 모듈](../../backend/data/README.md)과 [PR #5 인계](handoffs/2026-11-07-s-minjun-input-validation.md)에 있습니다. 다음 연결 검수는 API 담당과 실행 전 검사 연결이며, 등록 단계에서 누락 입력의 보관을 막지 않습니다.
- 원본과 정규화 결과를 연결하고 관측·모의·가정을 구분합니다. 반입시간과 선박 접안 예정시간을 같은 값으로 취급하지 않습니다.
- 누락 이동시간을 0으로 채우거나, 복귀 상태가 불명확한 차량을 즉시 사용 가능하다고 가정하지 않습니다.
- 정상·누락·잘못된 참조·준비 지연 등의 시나리오와 예상 판정을 준비합니다. 일정 계산의 기대 결과는 황대겸·안선효와 근거를 맞춥니다.
- **서비스 비교 반영:** 선석·반입시간·방문예약 자료의 의미와 출처를 분리합니다. 서류/검역 설명만으로 준비 완료를 가정하거나 상태를 새로 만들지 않고, 현재 `ready_at`의 의미와 누락 규칙을 지킵니다. 외부 기능이 존재한다는 사실과 우리 데이터 접근 권한을 구분합니다. 실제 TMS 배차 파일을 받으면 내보내기 허용·필드 대응을 확인한 뒤 기존 입력 변환 경로에 연결합니다.
- DB 테이블·저장 트랜잭션은 안선효 담당입니다. 심민준은 입력 변환·의미 검증·출처 관리를 맡고, 검증 결과와 스냅샷 생성에 필요한 값을 전달합니다.
- 외부 연동을 붙일 때는 권한·실제 응답·호출 한도·저장 허용 범위를 확인합니다. 가입 완료나 공개 화면 조회를 API 이용 승인으로 간주하지 않습니다.
- **API 사전 준비:** 체인포털 일반회원·현행 API 경로(AP-01), HJNC 요구 필드·연구용 접근(AP-02), 기상청 일반회원·본인 키(AP-05), 도로공사 후보 조건(AP-09)을 맡습니다. 항만 대외 연락은 대겸의 기존 문의와 조율하고, 본인 전용 키를 다른 팀원에게 넘기지 않습니다. [신청 안내](api-onboarding.md)의 순서와 완료 기준을 따릅니다.
- 인계물: 변환·검증 코드, 정상/오류 예제, 필드 대응과 시간대 근거, 재현 방법, 확인하지 못한 입력 목록.

## 03 · 황대겸 — 최적화 엔진·비교 실험

**완성할 것:** 같은 입력에서 원안의 위험과 조정안을 계산하고, 미처리·변경량·이동 부담 및 미해결 이유를 비교하는 엔진입니다.

- 구현 범위: B0 원안 위험 진단·B1 마감순 삽입·B2 이동 최소화·B3 변경 최소화를 비교합니다. 모든 조정 방법은 미처리 수를 우선하며, 고정 작업 보존과 미처리 근거를 확인합니다.
- B0~B3 구현·실험은 [엔진0.2.3 인계](handoffs/2026-11-08-unknownamed-engine-diagnostics.md)를 따릅니다. 완전한 초기안 힌트·probing0으로 탐색을 보완했고 엔진89개 검사를 통과했습니다. 최신 API·데이터 연결 후 전체 검수는 [통합 인계](handoffs/2026-11-08-pr12-pr14-integration.md)에 있습니다. [기존0.2.1·156회](../experiments/engine-sensitivity-2026-11-08/README.md)는 보존하며 [후속72회](../experiments/engine-profile-2026-11-08/README.md)와 구분합니다.
- 후속20건 B3는3초에서 변경2건의 최적성을 증명했고10초 호출 중앙값은5.21→2.42초입니다. 50건10초 B2는 전체 최적, B3는 미처리26/변경23/이동1,440분의 FEASIBLE로 전체 미증명입니다. [기존156회 PDF](../experiments/engine-report-2026-11-08/engine-experiment-summary.pdf)와 [후속72회 PDF](../experiments/engine-report-2026-11-08/engine-performance-followup.pdf)를 활용하되 모의 한계를 유지합니다. 다음은 리뷰 피드백·API/독립 검사 연결 대조·50건 B3의 남은 증명 병목 검증입니다.
- `solve(snapshot, method, config) → result`의 경계를 유지합니다. 엔진 안에서 DB·웹·외부 API를 호출하거나 입력을 수정하지 않습니다.
- 출발·고정 작업의 차량·순서·시각을 보존하고, 위험이 생겨도 작업을 삭제하거나 미처리로 바꿔 지표를 좋게 만들지 않습니다.
- 같은 입력·조건·계산 예산으로 B0~B3를 비교합니다. 입력 부족, 시간 내 해 미발견, 증명된 불가능을 구분하고 확인한 근거만 반환합니다.
- **서비스 비교 반영:** 출발 고정은 v0.1의 자동조정 범위로 유지합니다. B2/B3의 미처리 수준을 먼저 확인한 뒤 변경량·이동시간·계산시간의 절충을 비교합니다. 상용 TMS와 동일 조건으로 시험한 결과처럼 표현하지 않습니다.
- **API 사전 준비:** 엔진 자체는 외부 키 없이 개발합니다. 기존 BPA·HJNC 연락과 본인 계정 인증을 조율하고, SeaVantage 시험 API 문의(AP-03)·ShipsGo 대체 후보(AP-07)를 맡습니다. 승인 기간·사용 가능한 표본·체험 시점을 정리하고 API 대기 중에도 엔진과 비교 실험을 계속합니다.
- 안선효와 시간·고정·복귀·장비 조건을 함께 검토합니다. 안선효가 맡는 독립 일정 검사기를 통과해야 승인 가능한 결과가 됩니다.
- 인계물: 엔진 함수, 설정·버전·실행 기록, 재현 가능한 비교 결과, 실패·동률 사례와 미해결 근거.

팀장 역할은 범위와 진행 상황을 맞추는 일입니다. 다른 파트 구현이나 보고서·발표 전체 작성을 혼자 떠맡는 역할로 두지 않습니다.

## 04 · 안선효 — API·DB·통합

**완성할 것:** 입력을 저장하고 계산 실행·조회·결과 검증·내부 승인을 연결하는 백엔드입니다. DB 초기화·버전 관리, 요청 중복·오류·충돌 처리를 포함합니다.

- 첫 작업: 공통 입력의 등록·조회와 실행 상태·설명용 결과 조회를 연결합니다. 설명용 결과는 실제 계산으로 표시하거나 승인하지 않습니다.
- 데이터 모듈의 입력 검증과 엔진 함수를 호출합니다. 컨트롤러에 같은 변환·최적화 규칙을 다시 구현하지 않습니다.
- 엔진과 별도로 일정 검사기를 구현합니다. 작업 누락·중복, 고정 유지, 차량 점유 중복, 시간창·중량·호환·근무·복귀 조건을 다시 검사합니다.
- 입력 의미 검사는 심민준, 계산은 황대겸, **계산 결과의 독립 일정 검사와 승인 판단은 안선효**가 책임집니다. 각 단계의 검사 결과를 구분합니다.
- 실행 상태와 해 상태를 구분하고 계산이 화면 조회를 막지 않게 합니다. 승인 시 현재 입력·계획 버전을 다시 확인하며 같은 요청 재시도로 중복 승인이 생기지 않게 합니다.
- 인증·승인 구현 전에는 구현된 것처럼 표시하지 않습니다. 내부 승인은 외부 예약 변경이나 기사 통보를 뜻하지 않습니다.
- **서비스 비교 반영:** 외부 예약/관제 상태를 내부 승인 상태로 바꾸지 않습니다. 동일 공통 계약과 독립 일정 검사를 유지하고, 비교 자료에서 본 새 상태·필드·예약 변경 API를 임의 도입하지 않습니다. 변경 제안이 필요하면 데이터·엔진·프론트의 영향을 함께 남깁니다.
- **API 사전 준비:** AISstream 계정·서버 키(AP-06), 자동차 길찾기 서버 연동 조건(AP-08), SOLAPI 발신번호·명의 확인 절차(AP-10)를 맡습니다. 팀 외부 API의 비밀값 관리·사용량·캐시·오류 처리를 설계하되, 본인 전용 키를 전달받거나 실제 발송을 기본 활성화하지 않습니다. 내부 API 개발은 외부 서비스 이용 신청과 별개입니다.
- 인계물: API 실행 방법, DB 초기화·변경 절차, 계약·독립 일정 검사·승인 충돌 확인 기록, 비밀값 없는 설정 예시.

## 코드 경로와 공동 변경

리뷰는 [리뷰·병합 기준](review-policy.md)에 따라 필요한 큰 변경에 관련자가 1회 수행합니다. 아래 담당 경로는 모든 PR의 자동 리뷰 요청 대상이라는 뜻이 아닙니다.

다음은 담당별 코드 경로입니다. 프론트·API·DB·데이터 입력·B0~B3 엔진 구현이 있고, 실제 엔진 API·독립 일정 검사·로컬 내부 승인까지 연결했습니다. 전체 브라우저 시연과 운영 인증은 후속 작업입니다. 데이터 PR #5는 main에 병합됐습니다.

## 첫 공동 완료 기준

1. 같은 예제의 입력 → 저장 → 계산 상태 → 원안/조정안 비교 화면을 네 파트가 연결합니다.
2. J0 고정, J1/J2 조정, J3 미처리 이유를 모두 같은 ID와 기준시각으로 확인합니다.
3. 설명용 결과로 화면을 먼저 연결한 뒤 실제 엔진 결과로 교체합니다. 설명용 결과와 미검증 계산 결과는 승인하지 않습니다.
4. 실제 계산 결과는 독립 일정 검사 후 승인 조건을 확인합니다. 새 입력·계획 변경 뒤 이전 결과 승인과 동일 요청 중복 승인을 검사합니다.
5. 각 담당자가 자기 코드의 입력·출력·오류·검증 결과를 설명하고, 연결된 다른 파트 담당자와 확인합니다. AI가 작성했다는 이유로 검증을 생략하지 않습니다.

## 보고서·발표와 작업 인계

각자 담당 부분의 구현 방법, 실행 근거, 결과 화면 또는 비교 수치, 한계와 남은 일을 작성합니다. 이를 공통 보고서·발표로 모으며, 모의 실험 결과를 실제 운송 현장의 효과로 확대하지 않습니다.

작업을 넘길 때는 변경 파일, 사용한 계약 버전, 실행·검증 방법과 실제 결과, 미구현·미확인 사항, 다음 담당자의 할 일을 남깁니다. AI 대화 원문 전체를 공유 저장소에 올리는 대신 작업에 필요한 결정과 근거를 남기고, 개인정보·인증정보·서명·비공개 원자료는 포함하지 않습니다.
