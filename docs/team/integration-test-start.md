# 통합본 테스트 시작

2026-11-11 안내. 팀원은 완성한 파트를 다시 개발하기보다 통합본을 사용해 보고 결과를 전달합니다. 대겸이 결과를 모아 수정합니다. 이 문서는 사람과 저장소에 접근할 수 있는 AI가 함께 읽는 시작 안내입니다.

## 바로 시작하기

1. 기존 로컬 변경을 보존하면서 최신 main을 받습니다. [안전한 갱신 순서](../../CONTRIBUTING.md#최신-main을-반영하는-순서)를 따릅니다. AI에게 아래 문장으로 맡겨도 됩니다.
2. [테스트 웹앱](https://occasion-reporting-python-contacting.trycloudflare.com)을 엽니다. 웹 화면을 시험하는 데 별도 설치·API 키·로컬 서버 실행은 필요 없습니다. 대겸 PC 기반 임시 주소라 연결이 안 되면 시험 시각과 함께 알립니다.
3. [테스트 이슈 #69](https://github.com/unknownamed/banipmatch/issues/69)의 최신 안내에서 접속 주소·배포 버전을 확인하고, 아래 공통 항목과 자기 담당 항목을 시험합니다.

**문서 버전과 배포 코드 버전은 다릅니다.** 이 안내는 main에 있으므로 최신 main으로 읽을 수 있지만, 안내 작성 시점의 배포 코드는 PR #68의 `7b983a4428bc01e91c6654c85e98f2c45bf6d470`이며 PR68은 미병합입니다. 최신 main이라고 배포본과 같은 코드라고 판단하지 않습니다. 팀원이 PR68을 자기 브랜치에 합칠 필요는 없습니다. 원인 분석에 코드가 필요할 때만 해당 배포 커밋을 별도 검토 작업 폴더에서 읽습니다. PR68의 head가 나중에 바뀌어도 재배포 확인 없이 현재 서버가 갱신됐다고 하지 않습니다.

## AI에게 그대로 요청하기

이름만 바꿉니다. 프로젝트 폴더에서 사용하는 AI에게 전달합니다.

```text
나는 [이름]이야. 기존 작업을 보존하면서 최신 main을 받고,
AGENTS.md와 docs/team/integration-test-start.md를 읽어줘.
이슈 #69의 최신 주소·배포 버전을 확인하고 내 담당 통합 테스트를 진행해줘.
자동으로 가능한 검사는 수행하고, 휴대폰에서 내가 해야 할 일은 안내해줘.
문제와 재현 방법을 대겸에게 전달할 수 있게 정리하고, 못 한 검사는 미검증으로 남겨줘.
```

일반 웹 채팅 AI가 이 비공개 저장소를 읽지 못하면 이 문서와 필요한 자료를 직접 전달합니다. 링크만 주고 읽었다고 가정하지 않습니다. AI가 브라우저를 조작할 수 없으면 사람이 따라 할 순서를 제공하고, 실제 화면 검사는 미실행으로 남깁니다.

## AI의 진행 순서

1. 요청자 이름과 [역할표](roles.md)를 대조합니다. 이름을 모르면 담당만 확인하고 공통 시험부터 진행합니다. 기존 변경·미완성 작업을 덮어쓰지 않습니다.
2. 최신 main과 #69의 배포 버전을 구분해 기록합니다. 이전 개인 PR/자료를 기준으로 다른 버전을 검사하지 않습니다. 상세 배포 근거는 [7b983a4 통합 인계](https://github.com/unknownamed/banipmatch/blob/7b983a4428bc01e91c6654c85e98f2c45bf6d470/docs/team/handoffs/2026-11-11-unknownamed-live-demo.md), [같은 버전의 화면 검수표](https://github.com/unknownamed/banipmatch/blob/7b983a4428bc01e91c6654c85e98f2c45bf6d470/docs/team/frontend-release-checklist.md)를 확인합니다.
3. 배포 화면을 자기 브라우저 세션에서 검사합니다. 저장소의 전체 검사를 이유 없이 반복하지 않고, 새로운 실패·변경·담당 위험에 필요한 검사만 수행합니다. 실패를 모의 성공으로 바꾸거나 기대값에 맞춰 검사를 약화하지 않습니다.
4. 이번 요청은 테스트와 결과 인계입니다. 새 기능·API 재가입·결제·실기사 연락·main 병합·배포 서버 변경·보호 설정 완화를 임의로 하지 않습니다. 수정이 필요하면 재현과 수정 제안을 대겸에게 전달합니다. 별도 수정 요청을 받은 경우에는 기존 PR 규칙을 따릅니다.
5. 알림은 동의한 시험 참여자만 대상으로 하고, 대겸의 별도 기기 초대가 있어야 합니다. AI가 사람 대신 최초 알림 허용이나 실제 휴대폰 수신을 확인했다고 하지 않습니다. 사람 확인 전까지 실기기 항목은 미검증입니다.
6. 결과는 아래 양식으로 정리합니다. GitHub 댓글 작성 권한이 있는 요청이면 #69에 남기고, 없으면 팀원이 전달할 결과문을 제공합니다. API 키·세션 쿠키·구독 정보·개인 초대 링크는 출력/첨부하지 않습니다.

## 모두 확인할 것

예제01 선택 → 계산 요청 → 기존 배차/조정안 비교 → 위험 내용 확인 → 내부 승인 → **확정 계획으로 새 점검 시작** → 준비시각 등 조건 변경/이유 입력 → 재계산.

- 계산 중/완료/실패가 구별되는지, 새로고침·방법 전환 뒤 다른 결과가 섞이지 않는지 확인합니다.
- 해결되지 않은 작업의 이유를 이해할 수 있는지 확인합니다. 조건을 바꿨다고 항상 해결되는 것은 아닙니다.
- 배차와 움직이는 선박은 모의 데이터이며, 실제 수신 참고자료와 분리됩니다. 내부 승인으로 실제 운송·터미널 예약이 바뀌지 않습니다.

## 담당별 확인

| 담당 | 중점 확인 |
|---|---|
| 길웅 | PC/휴대폰 글자·표·버튼 잘림과 조작, 조건 입력, 모의 선박 재생/정지, 갱신 중단 선박의 회색 표시. 기본 지도는 OSM. 카카오 키/배포 도메인 설정 전 위성 지도가 표시된다고 가정하지 않음 |
| 민준 | 예제07 입력 부족 안내→보완 후 재계산, 예제08 미확정 변경 승인 차단. 실제/모의·관측/수신 시각·빈 값·실패 설명이 제공 자료와 맞는지 |
| 선효 | 승인 후 새 원안/재계산, 별도 브라우저 세션에서 다른 사람 결과 조회 차단, 초대·구독·전달 상태와 수행 응답 반영, 이전 지시 응답 차단 |
| 대겸 | 배포 버전/초대·시험 전송 준비, 결과 취합·통합 수정, 수정 부분 재시험 안내 |

길웅의 구현 인계 완료와 전체 서비스의 실기기 검수 완료는 구분합니다. 이번 안내는 길웅에게 새 기능 개발을 다시 배정하는 문서가 아닙니다.

## 휴대폰 알림 시험

Android 1대와 iPhone 1대를 목표로 합니다. 기종·OS/브라우저·가능한 시간을 #69 또는 팀 카톡에 알려주세요. **웹앱 주소만 여는 것으로 알림 등록이 되지 않습니다.** 대겸이 시험 직전에 기기별 초대 링크를 개인 전달합니다. 초대는30분·1회용이며 서로 공유하지 않습니다. 일반 방문자의 발송 차단은 정상입니다.

### Android

초대 링크를 **Chrome**으로 열기 → 초대 수락 → 알림 허용. 등록이 완료됐다고 대겸에게 알립니다.

### iPhone (iOS 16.4 이상)

초대 링크를 **Safari**로 열기 → 공유 메뉴의 **홈 화면에 추가** → 홈 화면에 생긴 반입맞춤 실행 → 화면 안내대로 초대 링크 붙여넣기 → 초대 수락 → 알림 허용. Safari 탭에서만 여는 것으로 대신하지 않습니다.

### 등록 후 함께 확인

1. 대겸이 시험용 배차를 내부 승인하고 변경 전달을 실행합니다. 실제 기사에게 보내지 않습니다.
2. 수신자는 휴대폰 화면을 잠가도 알림이 도착하는지 확인합니다.
3. 알림을 눌러 본인 차량의 변경 내용만 보이는지 확인합니다.
4. **수행 가능** 또는 **수행 곤란**으로 응답하고, 대겸은 담당자 화면의 응답/시각을 대조합니다.
5. 전달 접수, 실제 알림 도착, 열람, 사람 응답은 각각 기록합니다. 알림이 안 오면 OS·브라우저·허용 상태·화면에 보인 오류와 실패 단계만 기록하고 원인을 추측하지 않습니다.

카톡/문자가 아닌 웹앱 알림이라 전화번호는 필요 없습니다. 초대 수락·최초 권한 허용·잠금 화면 실수신은 참여자가 직접 합니다. 처음부터 실제 폰 검수가 끝난 기능으로 설명하지 않습니다.
