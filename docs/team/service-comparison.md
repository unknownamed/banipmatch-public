# 기존 서비스 비교와 개발에 반영할 사항

확인일: 2026-11-07. 공식 소개·앱 배포·공개 메뉴·매뉴얼을 비교한 기록입니다.
대상 서비스의 로그인 기능, 알고리즘, 실측 효과, API·학생 이용 권한은 검증하지 않았습니다.
팀과 AI는 [역할표](roles.md), [현재 상태](status.md), [공통 계약 v0.1](../development/v0.1/공통%20규격)을 함께 읽습니다.

## 이번 조사로 정한 방향

- 주제와 핵심 범위는 유지합니다. 기존 설계에 있던 경쟁 기능 중복을 구체적인 제품 근거로 보강합니다.
- 배차·지도·운송 추적·예약 변경·기사 알림·공차 감소 자체를 새 기능이라고 주장하지 않습니다.
- 검증할 가설은 **확인된 반입시간 변경 뒤 영향을 찾고, 같은 처리 수준에서 기존 작업의 변경 부담과 이동 부담을 비교할 수 있는가**입니다.
- 1차 사용자는 HJNC 일반 수출 Dry 업무를 맡은 운송사 배차 담당자입니다. 항만 전체 관제·검역·선석 운영으로 확대하지 않습니다.
- 공개 소개에서 찾지 못한 기능은 “미확인”입니다. “기능 없음”이나 “우리만 가능”으로 바꾸지 않습니다.

## 서로 다른 네 가지 결정과 시간

| 구분 | 결정·확인하는 주체 | 시간의 의미 | 우리 구현에서의 취급 |
|---|---|---|---|
| 선석·접안 | 해당 항만의 선석 운영 절차에 참여하는 운영자·선사·대리점 등 | 선박이 어느 선석에 언제 접안할지 | 선박 ETA·접안 변경을 반입마감 변경으로 자동 변환하지 않음 |
| 반입 허용시간 | 터미널의 공식 안내와 확인 절차 | 항차별 컨테이너 반입 시작·마감 | 확정된 이전/신규 값, 적용 항차, 출처·확인시각을 핵심 입력으로 사용 |
| 트럭 방문예약 | 터미널 예약 시스템과 신청 운송사·기사 | 특정 차량·방문에 배정된 슬롯·ETA | 항차 반입 허용시간과 별개. 슬롯이 있다고 모든 반입조건이 충족된 것은 아님 |
| 운송사 내부 배차 | 운송사 배차 담당자 | 어떤 작업을 어느 차량이 어떤 순서·시각에 수행할지 | 원안과 조정안, 미처리·변경·이동 부담을 비교하고 내부 승인 |

**출발 작업 고정은 현재 시제품의 자동 조정 범위입니다.** 실제 현장에서 출발 후 예약 변경이 절대 불가능하다는 뜻이 아닙니다. 현행 계약에서는 출발·고정 작업의 배정을 유지하며, 새 시간창에서 생긴 잔여 위험도 그대로 보고합니다. 현장 허용 범위를 확인하더라도 계약 변경 없이 잠금을 해제하지 않습니다.

## 7개 서비스의 확인 내용과 남은 질문

### 1. TIGER FACE — 직접적인 배차 업무 비교 대상

- **확인:** 개발사 소개에 운송 단계 추적, 화주·포워더의 운송 등록·승인·배차, 웹 배차현황·데이터 관리와 기사 앱이 있습니다. 같은 개발사의 Google Play 앱도 확인했습니다.
- **겹치는 부분:** 배차·업무 승인·운송상태·기사 화면. 이번에 제시된 세 제품 중 우리 운송사 업무와 직접 겹치는 부분이 가장 많습니다.
- **미확인:** 반입시간 변경의 자동 영향 분석, 여러 미출발 작업의 공동 조정, 변경량 최소화, 미해결 설명, 현재 운영 규모·효과와 외부 API 권한.
- **근거·한계:** [공식 개발사 소개][tiger] · [공식 배포 앱][tiger-app]. 포트폴리오와 앱 배포는 확인했으나 고객별 기능·실무 배차는 시험하지 않았습니다.

### 2. PortQM — 검역·서류 준비 상태 참고

- **확인:** 개발사는 항만 검역 관리와 포워딩 업무 전산화, 세관 업무·검역 데이터·서류 관리의 통합을 설명합니다.
- **겹치는 부분:** 항만 물류의 업무정보·처리 상태 관리. 운송사 배차 최적화와 직접 동일하다는 근거는 확인하지 못했습니다.
- **미확인:** 실제 운영 규모·효과, 실시간 지연 원인 API, 배차·재최적화 지원 여부.
- **적용:** 서류·검역 미완료를 차량 순서 변경만으로 해결한다고 표현하지 않습니다. **이번 수출 Dry 시제품에 신규 검역 모듈을 추가하라는 의미는 아닙니다.** 관련 원본 상태를 얻으면 준비 지연 근거로 연결할 수 있는지 검토합니다.
- **근거:** [공식 개발사 소개][portqm]. 공급자의 기능 설명이며 실제 처리 결과를 검증한 자료가 아닙니다.

### 3. UPA PortWise — 선박·선석 결정과의 구분

- **확인:** 공식 안내에는 AIS·Port-MIS 정보, 선박 크기·화물·입항예정·기상을 고려한 선석 배정, 정박 대기 관리·알림이 있습니다. 공개 메뉴에 선석·정박지 신청과 배정·대기순서가 있습니다.
- **겹치는 부분:** 지도·선박 위치·기상·일정 알림. 선박을 선석·접안시각에 배정하는 결정과 운송 작업을 차량·순서·시간에 배정하는 결정은 다릅니다.
- **미확인:** 소개된 AI 최적화의 알고리즘·실측 효과, 운송사 전체 배차의 최소 변경 지원, API·원자료 재사용 권한.
- **근거·한계:** [공식 안내][portwise-guide] · [선석 서비스][portwise-berth] · [UPA 플랫폼·앱 공지][portwise-news]. 선사·대리점·하역사 대상 안내와 공개 메뉴 확인 범위입니다.

### 4. CONTAINUS TMS — 국내 최적 배차와의 직접 비교

- **확인:** 엑셀 오더 입력, 그룹 오더 최적 배차, 운송현황 추적, 터미널 정보와 협력 운송사 배차·정산 공유를 명시합니다.
- **겹치는 부분:** 엑셀 입력·추천배차·상태 통합 자체는 차별점이 아닙니다.
- **미확인:** 반입시간 변경 이후의 고정 조건, 최소 변경 목적, 미해결 사유 제공 범위.
- **근거·주의:** [공식 TMS 소개][containus]. 소개의 “미마감/마감/정산”은 정산 기능 문맥이므로 컨테이너 반입마감 지원 근거로 읽지 않습니다.

### 5. 부산항 체인포털 VBS — 출발 뒤 예약 변경도 확인

- **확인:** 공개 앱 매뉴얼은 예약 확정·취소·출발, 운송 중 구간 통과와 예약 변경, 게이트·상하차·인수도 상태를 설명합니다.
- **겹치는 부분:** 예약·출발·상태·알림·운송 중 예약 변경. 이를 기존 서비스에 없는 기능으로 설명하지 않습니다.
- **미확인:** 현행 HJNC의 적용 범위·예약 변경 제한·수량, 운송사 전체 작업표의 최소 변경 재조정.
- **중요한 한계:** 2022년 화면이 포함된 [구판 매뉴얼][vbs]의 PDF 파일 10번째 페이지는 현재시각 3시간 이후와 터미널별 설정을, 13번째는 최소 30분 이후를 설명합니다. 이 차이를 임의로 통일하거나 HJNC의 현행 공통 규칙으로 적용하지 않습니다.

### 6. PSA Singapore OptETruck — 자동계획·공차 감소의 선행 사례

- **확인:** PSA는 실시간 자원 매칭, 예측 기반 자동 스케줄, 작업 추천, 공차 감소와 운송사 자원 공유를 설명하며 도입 운송사·고객 의견을 제시합니다.
- **겹치는 부분:** AI 배차·공차 감소라는 포괄적 주장은 이미 제공되는 기능과 겹칩니다.
- **미확인:** 확정 반입마감 변경에 대한 세부 재계산, 최소 변경 목적, 출발 작업 잠금과 미처리 설명.
- **근거·주의:** [PSA 공식 발표][optetruck]. 공급자 발표 성과를 독립 검증하거나 우리 모의 실험과 직접 비교하지 않습니다. 싱가포르 **OptETruck**은 기존에 조사한 앤트워프 **OptiTruck**과 별도 제품입니다.

### 7. ECT MyTerminal·TCMS / Portbase — 반입시간과 방문 슬롯

- **확인:** MyTerminal은 반입 시작·마감, 컨테이너 상태, 트럭 체류시간 정보를 안내합니다. TCMS FAQ는 Portbase 사전신고 ETA와 잔여 용량에 따른 슬롯, ETA 변경 시 슬롯 유지·재계산을 설명합니다. Portbase HCN에는 웹·API·EDI 연동 안내가 있습니다.
- **겹치는 부분:** 반입시간 조회·방문예약·지연 후 조정. 터미널 방문 슬롯 재배정과 운송사 하루 작업표 재배치는 구분합니다.
- **미확인:** 우리 범위의 최소 변경 목적과 전체 작업표 조정, HJNC에 적용 가능한 슬롯·입장 규칙.
- **근거·한계:** [MyTerminal][ect] · [TCMS FAQ][ect-faq] · [도입 공지][ect-news] · [Portbase HCN][portbase]. 9월 18일 공지는 10월 도입 계획이며 도입 완료 증명으로 쓰지 않습니다. 별도로 발견했던 주간 공지의 재조회가 404여서 운영 완료 근거에서 제외했습니다.

## 계약·실험·보고서에 적용하는 기준

- 이번 문서는 비교 근거와 설명을 보강합니다. **공통 v0.1 API·DB·스키마·예제와 기존 배포 PDF는 그대로 유지합니다.**
- PortWise의 선석 값, PortQM의 검역 상태, VBS의 예약 슬롯을 현재 객체에 개별 파트가 임의로 추가하지 않습니다. 새 필드가 필요하면 실제 표본·업무 의미·권한을 확인하고 영향을 받는 담당자와 새 계약 버전을 검토합니다.
- 현재 규격의 `additionalProperties:false`, 시간 단위·ID·출발 고정·독립 검사·승인 조건을 소개 페이지에 맞춰 약화하지 않습니다.
- `Job.state=departed`이면 `frozen=true`를 유지하고 고정 작업 잔여위험(`FIXED_RESIDUAL_RISK`)을 숨기지 않습니다. 현재 작업 상태는 `planned/departed`이며, 검역·서류 소개를 근거로 `blocked/customs_pending` 같은 상태를 추가하지 않습니다.
- `Window`는 `voyage_id + terminal_id`의 반입 `opens_at/closes_at`이며 차량 방문 슬롯 객체가 아닙니다. `ready_at`은 상차 완료 후 픽업지에서 출발 가능한 시각입니다. 미확인 `null`을 즉시 출발 가능으로 바꾸거나 별도 `readiness` 필드를 임의로 넣지 않습니다.
- 실행 상태, 해 상태, 미처리 사유, 근거 수준을 구분합니다. B2의 목적은 미처리 → 이동, B3는 미처리 → 변경 → 이동이며 새 제품 소개만으로 이 우선순위를 바꾸지 않습니다.
- B0~B3는 자체 비교 방법입니다. B2를 특정 상용 TMS의 재현으로 표시하지 않습니다. B2/B3의 처리 수준이 다르면 변경량만으로 우열을 말하지 않습니다.
- 작업 수행 감소가 포함된 이동량 감소를 곧바로 효율 개선으로 표현하지 않습니다. 미처리 수·변경 작업 수·이동시간·계산시간·잔여 위험을 함께 보고합니다.
- 공급자의 도입·효과 발표, 우리 모의 결과, 실제 운송사 평가를 분리합니다. “최초”, “기존 제품은 못함”, “현장 비용 절감 입증”은 현재 근거로 주장할 수 없습니다.
- 같은 기능이 현장에서 충분히 쓰인다는 근거가 나오면, 확인된 설명·검증·입력 편의의 공백으로 문제를 좁힐지 검토합니다. 기능 목록이 겹친다는 이유만으로 주제를 자동 변경하지 않습니다.
- 공유 저장소에는 필요한 판단·공식 링크만 남깁니다. 개인정보·로컬 절대경로·원문 채팅·서명·키·전체 HTML 수집 원본을 포함하지 않습니다.
