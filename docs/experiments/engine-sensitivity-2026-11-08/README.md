# 규모·예산·여유시간 비교 · 2026-11-08

엔진 `0.2.1-b0-b3`, OR-Tools `9.15.6755`, Python 3.12, 로컬 단일 worker. 모든 입력은 **인위적으로 만든 모의 자료**입니다. 현장 수요 분포·상용 TMS 성능을 대표하지 않습니다. [11월 7일 원본 실험](../engine-b0-b3/README.md)은 덮어쓰지 않았습니다.

## 실험 범위

| 묶음 | 조건 | 방법별 실행 합계 | 원본 결과 |
|---|---|---:|---|
| 규모 | 20건/4차량·50건/8차량, 1/3/10초, seed0, 각3회 | 72 | [JSONL](scale/results.jsonl) · [CSV](scale/runs.csv) · [집계](scale/aggregate.json) |
| 혼합 | 12건/4차량 2종, 3/10초, seed0/17/41 | 48 | [JSONL](mixed/results.jsonl) · [CSV](mixed/runs.csv) · [집계](mixed/aggregate.json) |
| 여유시간 | 고정 없는 혼합12건, 여유0/10/20분, 3초, seed0, 각3회 | 36 | [JSONL](buffer/results.jsonl) · [CSV](buffer/runs.csv) · [집계](buffer/aggregate.json) |

총39조건에서 B0~B3를 각각 실행한 **156회**입니다. 같은 조건의 방법들은 동일 입력 해시·원안·시드·총 시간 예산을 받습니다. 라이브러리는 측정 전에 로딩하고, 실행은 순차로 진행했습니다. 규모·여유 묶음은 동일 시드의 시간 변동을, 혼합 묶음은 서로 다른 시드의 해를 확인합니다. 모집단 통계나 신뢰구간을 산출한 실험은 아닙니다.

각 폴더의 `metadata.json`에 Python/환경·방법별 예산·입력 해시·실제 엔진 소스 SHA-256을 남겼습니다. `git_head`는 실행 당시 기반 커밋이며, 아직 커밋하지 않은 구현까지 식별하는 것은 `source_sha256`입니다. `results.jsonl`에는 배정·미처리·각 목적 단계 상태/값/하한을 포함한 전체 결과가 있습니다. 완료 전 중단된 실험은 `completed=false`로 남습니다.

## 규모에 따른 결과

숫자는 **미처리 / 변경 작업 / 조정 작업 이동분**입니다. B1은 20건에서 `8 / 12 / 720`, 50건에서 `26 / 24 / 1440`이었습니다.

| 입력·예산 | B2 | B3 | 반복3회에서 확인한 상태 |
|---|---|---|---|
| 20건·1초 | 8 / 12 / 720 | 8 / 12 / 720 | 미처리 목적만 증명, 나머지는 미완료 |
| 20건·3초 | 8 / 12 / 720 | 8 / 10 / 720 | B2 전체 최적, B3 변경 단계 미증명 |
| 20건·10초 | 8 / 12 / 720 | 8 / 2 / 720 | 두 방법 모두 전체 최적 |
| 50건·1/3/10초 | 26 / 24 / 1440 | 26 / 24 / 1440 | 초기 유효안 유지, 솔버 첫 단계 UNKNOWN |

20건·10초에서 B3는 처리 건수와 이동량을 유지하면서 변경을12→2건으로 줄였습니다. B3 실제 소요시간 중앙값은 약5.21초(5.20~5.25초), B2는 약1.46초였습니다. 3초에서는 B3 변경10건을 얻었지만 그 값이 최선이라고 증명하지 못했습니다.

20/50건은 단일 시간창·같은 이동구조의 단순 사례입니다. 차량당 접근20+적재30+복귀10분으로 첫 도착50분, 다음110분, 다음170분이며 네 번째230분은 마감180분을 넘습니다. 차량당 최대3건이므로 미처리8/26은 이 사례의 수작업 하한과 일치합니다. 코드의 `objective_proven`은 실제 솔버 단계 결과만 표시하며 이 설명을 근거로 강제로 true로 바꾸지 않습니다.

0.2.1은 기존 시간 제약을 합친 [차량별 작업량 한계](../../../backend/engine/OPTIMIZATION.md)를 중복 제약으로 추가했습니다. 20건에서는 미처리 증명 이후 변경·이동 단계까지 진행했습니다. 50건은 개선되지 않았습니다. 10초에서도 솔버의 첫 해를 찾지 못해 B1 초기안을 유지했으므로, 큰 입력의 최적화 성능이 해결됐다고 할 수 없습니다. 1초 예산의 실제 전체 호출은 약1.04초로 끝나기도 했습니다. 이 예산은 강제 프로세스 종료 보장이 아닙니다.

## 업무 조건이 섞인 12건

[혼합 입력](inputs/mixed_12.json)은 DRY20·DRY40, 서로 다른 허용중량, 항차3개와 시간창3개, 준비 지연·처리시간을 포함합니다. [고정 포함 입력](inputs/mixed_fixed_12.json)은 여기에 이미 출발한1건과 미래 고정 예약1건을 넣었습니다. 고정 출발 기록의 이른 반입 위험1건을 의도적으로 남겼습니다. 입력 생성기는 [build_engine_benchmarks.py](../../../tools/build_engine_benchmarks.py)이며 데이터 모듈의 입력 검사를 통과합니다.

| 입력(여유10분) | B1 | B2 | B3 | 보존 조건 |
|---|---:|---:|---:|---|
| 혼합12건 | 3 / 8 / 540 | 3 / 8 / 540 | 3 / 5 / 540 | 조정 작업 위반0 |
| 고정 포함12건 | 3 / 7 / 420 | 3 / 7 / 420 | 3 / 5 / 420 | 고정2건 그대로, 잔여 위험1건 유지 |

3/10초와 시드0/17/41의 모든 실행에서 B2/B3 목적값이 같고 전체 최적성이 증명됐습니다. 동률인 구체적 배정까지 동일해야 한다는 뜻은 아닙니다. 이동 합계는 조정 작업에 한정하므로 고정 포함 입력의420분을 고정 없는 입력의540분보다 효율적이라고 비교하지 않습니다.

## 여유시간 민감도

| 여유시간 | B1 | B2 | B3 |
|---|---:|---:|---:|
| 0분 | 2 / 9 / 600 | 2 / 9 / 600 | 2 / 6 / 600 |
| 10분 | 3 / 8 / 540 | 3 / 8 / 540 | 3 / 5 / 540 |
| 20분 | 3 / 6 / 540 | 3 / 6 / 540 | 3 / 5 / 540 |

여유0→10분에서 미처리가2→3건으로 늘었습니다. 이동600→540분은 처리 작업이 줄어든 결과를 포함하므로 효율 개선으로 해석하지 않습니다. 원안의 기록된 시각은 모든 변형에서 그대로 보존했습니다. 여유값이 달라지면 B0의 기록 복귀와 현 정책의 계산 복귀가 달라져 위반 진단이 추가될 수 있습니다. 따라서 B0의 전체 위반 수를 마감 위반 수로 부르지 않습니다. 고정 시각까지 다시 만들어 민감도 효과를 숨기지 않기 위해 이 묶음은 고정 없는 입력을 사용했습니다.

## 검증·재현·다음 판단

- 전체 Python167개/하위156개, 계약·예제29개+DB32개 통과. 엔진82개에는 양수 여유시간·복귀/재사용·배열 순서 독립성·작업량 한계 회귀 검사가 있습니다.
- [156회 결과 검수](checks.json): 결과 스키마·입력/소스 해시·작업 분할·고정 기록 보존 확인. B1/B2/B3의 조정 작업 위반은 모두0입니다. **API 담당 독립 일정 검사기 완료를 뜻하지 않습니다.** 모든 결과는 `not_run/approval_eligible=false`입니다.
- 12~20건 혼합 입력은 현재 내부 시연 후보입니다. API 연결 시 실제 프로세스 시간 제한·화면 대기/실패 처리를 함께 검증해야 합니다. 50건은 제한시간 결과 표시·유효 초기안 유지의 사례로 쓰고, 대량 최적화 완료로 소개하지 않습니다.
- 다음 성능 작업은 50건 전처리/경로 조합 탐색의 병목 분석입니다. 근거 없이 worker 수·배포 동시 실행을 늘리지 않습니다. 실제 배차 자료와 검증된 반입시간 출처 확보도 별개입니다.
