# 고정 조건의 새 모의 평가 · 2026-11-08

황대겸 담당의 비교 실험과 심사 근거 보완이다. 원래 엔진·계약·과거 156회 및 72회 결과는 변경하지 않는다. 현장 표본이나 상용 TMS 비교가 아니다.

## 실행 전에 정한 조건

- 기반 main `e2d9151c593536e66381d2f6268cb484c5ed90da`, 엔진 `0.2.3-b0-b3`의 설정 유지. 새 평가 결과로 모형·탐색 파라미터를 조정하지 않는다.
- [protocol.json](protocol.json)에 생성·솔버 시드, 모든 입력 해시, 엔진 소스 해시, 시간 예산을 고정했다. 계산 전에 생성한 파일이다. 결과가 나쁜 입력도 제외하지 않는다.
- 8건/3차량 입력 8개: 마감 단축·시작 지연·준비 지연·고정 작업 위험의 4종 × 생성 시드 101·202. 각 방법 총 예산 3초.
- 추가 규모 사례: 20건/4차량(생성 시드303), 50건/8차량(404), 각각 총 예산10초. 큰 입력도 같은 모형과 설정을 사용한다.
- 10개 입력 × 솔버 시드0·17 × B0/B1/B2/B3 = **80회 계산**. 솔버 시드 반복은 독립 현장 표본을 늘린 것이 아니다.
- 완전한 방향별 합성 이동표, 이동8~30분, 서비스5·10·15분, 여유10분, 근무600분. 준비0~60분 또는 준비지연350분. 도로·게이트 실측값이 아니다.
- [생성 도구](../../../tools/build_evaluation_inputs.py)는 솔버를 호출하지 않는다. 원안은 이전 시간창에서 순차적으로 만들고, V1의 시간창만 변경한다. [변경 전 입력](before-event/)과 [평가 입력](inputs/)을 모두 보존한다.

새 입력은 개발 중 파라미터 선택에 사용하지 않은 합성 사례다. 작은 8개는 두 기본 난수 구조를 네 프로필로 변형한 상관 사례다. 같은 팀이 기존 코드와 제약을 알고 생성했으므로, 독립적으로 수집한 현실 분포의 홀드아웃이나 외부 검증 자료라고 부르지 않는다.

## 확인할 항목

1. 모든 계산이 같은 입력을 받고 입력을 변경하지 않는가.
2. 원안·고정 작업·전체 작업 집합이 보존되는가.
3. API 담당의 별도 일정 검사기로 조정 결과·지표를 다시 확인하는가. B0는 위험 진단용 원안이므로 별도 일정 승인 대상으로 세지 않는다.
4. B2/B3의 미처리 수가 같은가. 같더라도 실제 처리 작업 ID가 다르면 별도로 표시한다.
5. 변경 합집합·이동시간·고정 잔여 위험·실행시간·목적 단계별 증명 상태를 함께 보여주는가.
6. 검증 실패·시간 초과·미증명·불리한 비교도 전체 결과에 남기는가.

원시 엔진 결과의 `validation_status=not_run`, `approval_eligible=false`는 그대로 보존한다. 실험에서 수행한 독립 검사 결과는 별도 필드에 기록하며, 실제 내부 승인이나 외부 예약 변경을 수행하지 않는다. 독립 일정 검사는 실행 가능한 결과를 확인하는 것이며 전체 최적성 증명은 솔버 상태 또는 작은 완전열거와 구분한다.

## 지표 해석

`changed_job_ids`는 차량·허용폭 초과 출발시각·순서 역전·신규 배정의 합집합이다. 미처리로 빠진 작업은 변경 수에 포함되지 않으므로 **미처리부터 먼저 비교**한다. 이동시간은 조정 가능한 작업의 접근·적재·복귀 구간 합계이며 고정 운송과 서비스·여유시간을 포함하지 않는다. B2의 변경 수는 이동 최소화 목적의 동률 해 선택에도 영향을 받는다.

수치가 줄었다고 현장 업무시간·비용·탄소가 같은 비율로 줄었다고 말하지 않는다. 같은 미처리 수와 같은 처리 작업 집합을 구분하고, 상충하는 이동 부담·미처리·고정 위험을 함께 설명한다.

## 재현

저장소 루트에서 기존 백엔드 개발 의존성을 설치한 후:

```sh
python tools/evaluate_engine.py --protocol docs/experiments/engine-evaluation-2026-11-08/protocol.json --output-dir local/evaluation-replay
python -m pytest tests/engine/test_optimization_oracle.py tests/engine/test_evaluation.py -q
```

기존 출력 폴더를 덮어쓰지 않는다. 동일 버전이라도 제한시간·실행환경에 따라 탐색 결과가 달라질 수 있다. 소스가 바뀌면 해시 검사를 통과시키려고 이전 프로토콜을 고치지 말고 새 평가 묶음을 만든다.

## 확인한 결과

실행 커밋 `0d2640bec9886fe344166809123bc9a2cc19bb92`에서 80회 모두 완료했다. 오류·누락 0회, B1/B2/B3의 독립 검사 60/60 통과, B0 원안 보존 검사 20/20 통과다. 변경 전 원안 10개도 [별도 확인 기록](before-event-checks.json)에서 미처리·조정 위반·고정 위험이 모두 0이었다.

- B2/B3 전체 20쌍이 같은 미처리 수와 고정 위험을 보였다. 이 중 **14쌍만 처리 작업 집합도 동일**하다.
- 같은 작업 집합의 작은 사례 12쌍에서 B3 변경 수는 4~7건 감소했지만 이동은 **12~82분 증가**했다.
- 나머지 같은 집합 2쌍은 50건 사례다. 두 방법 모두 미처리9·변경41·이동1,860분으로 차이가 없었다. 이 사례에서는 B3의 이점이나 최적성을 확인하지 못했다.
- 다른 작업 집합의 6쌍은 고정 사례4쌍·20건 사례2쌍이다. 같은 업무의 효율 개선처럼 합치지 않는다. 고정 사례는 두 방법 모두 고정 잔여 위험1건을 유지했다.
- B2/B3 40회 중 전체 최적성 증명35회(B2 18/20, B3 17/20). 20건 B3 시드0은 미처리·변경까지만 증명하고 이동은 미증명이며, 시드17은 전체 증명했다. 50건 네 번은 모두 첫 단계 FEASIBLE이다.

다음 대표 행은 솔버 시드0이며 **변경 수와 이동은 B2 → B3**다. 유리한 행만 제시하지 않도록 모든 프로필과 두 규모를 포함했다. 시드17과 모든 상세 결과도 아래에 공개한다.

**결론은 선택의 절충이다.** 변경 최소화 목적을 넣었으니 변경이 줄었다는 사실만으로 기존 배차 서비스보다 우수하다고 주장하지 않는다. 증가한 이동 부담, 미처리, 고정 위험, 제한시간을 함께 제시하고 실제 사용자에게 변경 감소의 가치가 있는지 후속 확인한다. 고정 방법 순서·시드별 1회 측정이므로 일반적인 실행시간 우위도 주장하지 않는다.
