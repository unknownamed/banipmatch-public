# 프론트 (최길웅)

배차 담당자용 단일 작업 화면. 현재는 **공통 예제(v0.1) 설명용 결과를 표시하는 단계**이며 로컬 API의 입력 등록·실행 요청·결과 조회에 연결했다. API의 실제 최적화 엔진 연결과 독립 일정 검사·승인은 아직 구현하지 않았다.

## 도구

React 18 + TypeScript + Vite 6.4.5, 테스트는 Vitest 4.1.12. 상태 관리·UI 라이브러리는 쓰지 않았다. 개발 도구의 알려진 취약점을 줄이기 위해 버전과 잠금 파일을 함께 갱신했다(2026-11-08 `npm audit` 보고 0건이며 모든 보안 문제의 부재를 보장하지 않음).

## 실행

Node 24 권장(CI와 같은 버전). Vitest는 Node 20·22·24 이상 지원 계열을 사용한다.

```sh
cd frontend
npm ci --ignore-scripts
npm run dev        # http://localhost:5173
npm test           # 공통 예제 판정 테스트
npm run build      # 타입 검사 + 빌드
```

PR과 main 변경마다 위 테스트·빌드를 GitHub Actions가 실행한다. 실제 브라우저 조작과 전체 API 연결 검수는 별도로 남긴다.

- 기본은 fixture 모드: `docs/development/v0.1/예제 데이터`의 01·03·04 JSON을 **복사하지 않고 직접** 읽는다.
- [백엔드 안내](../backend/README.md)에 따라 로컬 API를 실행한 뒤 `frontend/.env.local`에 `VITE_API_MODE=http`와 서버 모의 토큰과 같은 `VITE_API_TOKEN`을 설정하고 개발 서버를 시작한다. `.env.example`을 참고하며 실제 설정값은 Git에 올리지 않는다. `/v1` 요청은 `127.0.0.1:8000`으로 전달한다(포트는 백엔드에 맞춰 `vite.config.ts` 수정).
- HTTP 모드에서 `?run=`이 없으면 **예제로 계산 요청** 화면이 뜬다. 버튼을 누르면 새 ID로 `POST /v1/scenarios`, `POST /v1/runs`를 보내고 받은 `run_id` 결과 화면으로 이동한다. 실패 후 다시 시도는 같은 본문·같은 Idempotency-Key를 쓴다. 로컬 API로 등록201 → 실행202 → 결과200과 설명용 결과의 승인 차단을 확인했다.
- 계산 방법은 B0~B3 체크박스로 고른다(기본 전체, B0는 비교 기준이라 항상 포함). 방법이 바뀌면 실행 요청 멱등키도 바뀐다. 설명용 모드 서버는 B1/B2에 `422 DEMO_METHOD_UNAVAILABLE`을 주므로 입력 거절이 아닌 "방법을 바꿔 다시 요청" 안내로 표시한다.
- 입력 예제는 01·07(입력 누락)·08(미확인 변경) 중 고른다. 07의 422 입력 오류·08의 `503 WINDOW_UNCONFIRMED`처럼 입력 확인이 필요하면 원안과 거절 사유를 보여주고 재시도 버튼은 숨긴다. `503 STORAGE_UNAVAILABLE` 등 일시 장애에는 오류 안내와 같은 요청의 재시도를 유지한다.
- 승인은 approvalGate를 통과하고 미처리·고정 위험 작업 확인 체크 후에만 `POST /v1/plans/{plan_id}/approvals`를 보낸다. 승인 응답과 `GET /v1/plans/{plan_id}`의 현재 계획을 대조하고, 409·422·503은 오류 코드별 할 일을 안내한다. 현재 서버는 설명용 결과만 주므로 실제 승인 저장 성공은 아직 확인하지 못했다.
- 다른 ID 조회: `?scenario=S001&run=R001`.

## 지키는 규칙

- 변경 여부·원인은 응답의 `metrics`, `issues`만 쓴다. 화면에서 원인을 만들어내지 않는다.
- `illustrative_fixture` 결과는 배너로 표시하고 승인 버튼을 막는다.
- 계산 중에도 입력·변경 근거는 먼저 보인다. 등록·계산·승인 POST는 사용자 동작 없이 자동 반복하지 않는다.

## 승인 요청 검수 범위 (PR #9)

- 입력·실행·결과의 ID와 기준 계획 버전, 전체 해 상태를 검사하고 미처리·고정 위험 작업을 확인한 뒤 보낸다. 서버는 현재 입력·계획 버전과 권한을 승인 트랜잭션에서 다시 검사해야 한다.
- 통신 실패로 결과를 모르거나 저장소 장애가 나면 같은 본문과 멱등키로 재시도한다. 화면 안에서 방법을 바꿨다가 돌아와도 요청 키를 유지하며, 미처리·고정 위험 작업을 다시 확인한 뒤 재시도할 수 있다. 전체 페이지를 새로고침하면 이 메모리 캐시는 초기화되므로 현재 계획부터 확인한다.
- 버전 충돌·입력 거절·미확인 근거·승인 기능 미구현 응답 뒤에는 오래된 요청을 반복하지 않는다. 다른 계획·실행·방법·버전 또는 외부 반영을 보고한 성공 응답도 승인 완료로 표시하지 않는다.
- 유효한 승인 응답 뒤 현재 계획 조회 실패 또는 버전·입력·승인 ID 차이를 별도 경고한다. 조회 실패를 승인 POST 실패로 취급해 다시 보내지 않는다.
- `npm test`에는 jsdom의 실제 React DOM 클릭·상태 전이 회귀가 포함된다. 승인 성공·응답 유실·버전 충돌은 모의 HTTP 클라이언트로 검증한 것으로, 서버의 승인 저장·인증·동시성 구현이 완료됐다는 의미는 아니다.


## 담당자 대응 흐름 (v0.2 · #55)

`VITE_API_MODE=v2`로 개발 서버를 켜면 `/v2`(담당자 대응 API)에 연결한다. 서버는 `BANIPMATCH_WORKFLOW=1`로 실행한다([서버 안내](../backend/workflow/README.md)). 관리자 토큰을 쓰지 않고 서버가 주는 HttpOnly 세션 쿠키를 쓰며, CSRF 값은 화면 메모리에만 둔다. 개발 서버 주소는 서버 허용 출처인 `localhost:5173`이어야 한다.

| 화면 | 하는 일 | 파일 |
|---|---|---|
| 계산 요청 | 서버가 현재 시각으로 옮긴 모의 예제 01을 등록·계산(07·08은 원래 시각 그대로) | `api/v2.ts`, `StartRunPanel.tsx` |
| 조건 보완·재계산(R4) | 준비·가용·근무 시각만 24시간제로 수정, 확인된 조건(모의)/가정 시험 구분, 수정 이유 필수 → 새 입력 저장 후 같은 방법·예산·seed로 재계산 → 서버 전후 비교와 한계 표시. 가정 시험은 승인 차단 | `RevisionPanels.tsx`, `lib/revision.ts` |
| 변경 전달·응답(R5~R7) | 승인 뒤 차량별 변경 명세·확인할 사항, 시험 수신자 초대(허가 세션만, 비밀은 링크 `#`), 확인 체크 후 전달(승인당 멱등키 1개), 대상별 전달·사람 응답 상태 5초 갱신, 확실한 실패만 재시도 | `DispatchPanel.tsx`, `lib/dispatch.ts` |
| 수신자 `/recipient` | 초대 수락(링크 `#invite=`를 시작 시 한 번 읽고 주소에서 지움, 해시 기반 수락 키), iPhone Safari는 홈 화면 추가 안내만, 알림 허용·끄기, 내 차량 변경만 보기, 확인·수행 가능·곤란 응답, 이전 계획은 상세·응답 차단 | `RecipientApp.tsx`, `api/recipient.ts`, `lib/recipient.ts` |
| 수신자 모의 `/recipient?demo=1` | 서버·푸시 없이 탭 메모리의 가짜 자료로 수신자 화면 확인 | `api/recipientDemo.ts` |

`public/sw.js`는 푸시를 받으면 일반 문구만 보여주고 알림을 누르면 `/recipient#notification=ID`를 연다. `public/manifest.webmanifest`·아이콘은 수신자 화면에서만 연결한다.

배포 시 확인할 것: `/v2/*`는 백엔드로 전달하고 `/recipient` 직접 방문·새로고침은 `index.html`로 돌려준다(API 오류를 HTML 200으로 바꾸지 않음). `sw.js`는 사이트 루트에서 제공해야 한다. 실제 알림은 HTTPS와 서버 VAPID 설정이 있어야 하며 로컬 HTTP에서는 확인하지 않았다.

## 공개용 읽기 전용 계산 기록

`npm run build:showcase`는 `dist-showcase/`에 별도 정적 사이트를 만듭니다.
`npm run preview:showcase -- --host 127.0.0.1 --port 4174`로 빌드 결과를 확인합니다.
배포 시 `dist-showcase/` 내용만 게시합니다. 상대 경로를 사용하므로 `/demo/` 같은 하위 경로에서도 동작합니다.
일반 `npm run build`와 기존 로컬 API·실행·내부 승인 화면은 그대로 유지됩니다.

- 입력은 `docs/experiments/engine-evaluation-2026-11-08/showcase.json` 한 개를 빌드에 포함합니다. 보존된 실제 계산 기록이며 새 계산·수작업 설명용 결과가 아닙니다.
- 10개 모의 입력의 계산 시드0·B0~B3 40개 기록을 보여주고, 전체80회·20비교쌍의 맥락과 불리한 결과도 함께 제공합니다.
- 원본 `validation_status: not_run`과 `approval_eligible: false`를 유지하고, 별도 독립 감사를 구분합니다. 조회용 `Run`을 만들거나 내부 승인 상태로 바꾸지 않습니다.
- `showcase/`는 독립 진입점입니다. API 클라이언트·지도·실행·승인 코드를 불러오지 않습니다. URL 쿼리로 HTTP/지도 모드에 진입할 수 없습니다.
- 별도 빌드 설정에는 개발 프록시가 없고, 환경파일·공용 정적 폴더·소스맵을 포함하지 않습니다. HTML CSP는 네트워크 연결을 `connect-src 'none'`으로 막습니다.
- 실제 배차표·GPS·현장 효과, 새 계산·사용자 인증·다중 사용자 저장은 공개 아카이브 범위 밖입니다.

브라우저 정책상 파일을 직접 여는 대신 정적 HTTP 서버로 제공해야 합니다. 공개 배포의 보안 헤더·호스팅 설정은 게시 환경에서 별도로 확인합니다.
