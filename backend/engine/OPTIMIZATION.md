# B2/B3 모형과 판정 범위

기준: 엔진 `0.2.4-b0-b3`, 공통 계약 `v0.1.0`, OR-Tools `9.15.6755`. 함수는 기존 `solve(snapshot, method, config)`를 유지합니다. DB·웹·외부 수집·내부 승인 상태를 변경하지 않습니다.

## 무엇을 결정하는가

작업별 배정 여부·차량·정수 순서·분 단위 출발시각을 결정합니다. 차량별 선택 경로는 CP-SAT Circuit으로 표현합니다. 배정하지 않은 후보는 자기 자신으로 연결하고, 선택한 작업은 시작 노드와 하나의 경로를 이룹니다. 경로를 따라 순서가 증가하도록 해 이동시간이 0인 구간에서도 순서를 보존합니다.

시간 제약은 시작 가용시각 또는 앞 작업 복귀에 접근시간을 더한 이후 출발, 준비 이후 출발, 반입 시작 이후 도착, 도착+여유가 마감 이내, 처리·복귀까지 근무 종료 이내입니다. 방향별 이동시간을 사용하고 장비·중량에 맞는 차량만 후보로 둡니다.

이미 출발한 고정 작업은 최적화 경로 밖의 과거 기록으로 보존합니다. 차량의 확정 가용시각·위치에서 남은 경로를 시작합니다. 미래 고정 예약은 차량·순서 정수·출발·도착·복귀를 그대로 둔 필수 노드입니다. 고정 작업의 새 마감 위반은 잔여 위험으로 보고하며, 해당 작업을 제거하거나 선택 작업의 하드 제약처럼 전체 불능을 만들지 않습니다. 고정 기록 자체의 모순이나 고정 예약 사이 접근 불확실성은 해당 차량의 신규 배정을 막고 입력 부족으로 알립니다.

## 차량별 작업량 한계 · 0.2.1

한 차량이 선택한 경로의 접근시간과 작업별 점유시간 합은 마지막 복귀시각에서 차량 가용시각을 뺀 값을 넘을 수 없습니다. 기존 경로별 시간 부등식을 더하면 대기시간만 빠지고 이 조건이 남습니다. 이를 중복 제약으로 직접 넣어 탐색을 돕습니다.

- 조정 작업의 최후 복귀는 `min(근무 종료, 마감 + 처리 + 복귀 이동)` 이하입니다. 마감이 도착+여유를 제한하므로 이 식에서는 적재 이동과 여유시간이 상쇄됩니다.
- 미래 고정 예약은 기록된 `복귀−출발` 점유와 실제 복귀시각을 씁니다. 근무를 넘는 잔여 위험 때문에 원래 고정 작업을 제거하지 않습니다. 이미 출발한 작업은 차량 가용 상태에 반영됐으므로 다시 합산하지 않습니다.
- 상한은 차량 가용시각·후보들의 최후 복귀·고정 복귀 중 최댓값입니다. 빈 경로도 허용합니다. 접근은 실제 선택한 직전 작업의 구간을 사용하며 삼각부등식을 가정하지 않습니다.

이 제약은 목적이나 가능한 일정의 범위를 바꾸지 않습니다. 양수 여유시간, 0시간 작업, 비삼각 이동행렬, 고정 작업의 근무 초과, 늦은 가용시각을 회귀 검사합니다.

## 완전한 초기안 힌트와 탐색 설정 · 0.2.2

초기 유효안에서 배정·차량·경로·순서·출발시각뿐 아니라 변경 여부의 AND/OR·시각 비교·상대순서 비교 등 보조변수 값까지 계산해 모든 모형 변수에 힌트를 제공합니다. 힌트는 제약이 아니며 솔버가 유효성과 목적값을 검사합니다. 다음 목적 단계의 힌트도 현재 후보로 다시 구성합니다.

OR-Tools9.15의 `cp_model_probing_level` 기본값은2이며0은 probing을 끕니다([공식 파라미터 정의](https://github.com/google/or-tools/blob/v9.15/ortools/sat/sat_parameters.proto), 조회2026-11-08). 이 엔진은 이를0으로 설정하고 `cp_model_presolve` 등 나머지 전처리는 유지합니다. 조밀한 경로 모형의 짧은 예산이 probing에 소진되던 관측에 대응한 설정이며, 기존 제약·목적·작업량 한계와 가능한 일정은 그대로입니다. 모든 입력에서 더 빠르다는 보장은 아닙니다.

[정식 후속72회](../../docs/experiments/engine-profile-2026-11-08/README.md)에서20건 B3는3초에도 변경2건의 최적성을 증명했고10초 호출 시간 중앙값은5.21→2.42초였습니다. 50건10초 B2는3회 모두 전체 최적, B3는 미처리26/변경23/이동1,440분이며 단계별 `OPTIMAL/FEASIBLE/NOT_RUN`으로 전체 최적성이 미증명입니다. 50건3초는 두 방법 모두 첫 목적이 `FEASIBLE`이었습니다. 진단4회 로그 시간은 정식 비교에 합치지 않습니다.

[기존0.2.1·156회 PDF](../../docs/experiments/engine-report-2026-11-08/engine-experiment-summary.pdf)와 [후속0.2.2·72회 PDF](../../docs/experiments/engine-report-2026-11-08/engine-performance-followup.pdf)를 분리 보존합니다. 검사는 엔진86개·전체 Python171개/하위156개·계약29개·DB32개 통과이며 API 독립 일정 검사·승인은 여전히 별도입니다. [최신 인계](../../docs/team/handoffs/2026-11-08-unknownamed-engine-performance.md)에 다음 검증을 남깁니다.

## 시간 초과 시 입력 누락 보존 · 0.2.3

모형 생성자가 중간에 시간 초과로 끝나면, 그때까지 발견한 입력 문제를 예외에 담아 반환 경로에 전달합니다. 초기안 구성 중 발견한 누락과 차량 가용 상태의 누락도 보존합니다. 따라서 차량 `available_at`이나 후보 접근 경로가 미확정인 입력을 계산 시간만 부족한 `UNKNOWN`으로 바꾸지 않고, `INPUT_INCOMPLETE`와 근거를 함께 제공합니다. 계산하지 않은 목적 단계는 계속 `NOT_RUN`, 최적성·승인 가능 여부는 false입니다. 입력이 충분한 시간 초과는 기존 유효안과 `FEASIBLE` 판정을 유지합니다.

변경은 진단 보존에 한정되며 목적·가능해·완료된 탐색의 결과는 바꾸지 않습니다. [회귀와 연결 인계](../../docs/team/handoffs/2026-11-08-unknownamed-engine-diagnostics.md)를 따릅니다. 앞선 성능 PDF와72회 실험은0.2.2 결과로 보존하며0.2.3에서 재측정한 것으로 표시하지 않습니다.

## 동률 안에서 원안 출발시각 유지 · 0.2.4

정책의 `time_change_tolerance_minutes`(예제 5분) 안의 출발 이동은 변경으로 세지 않으므로, 목적값이 같은 일정이 여럿 있습니다. 0.2.3까지는 솔버가 이 가운데 아무 출발시각이나 골라 바뀌지 않은 작업도 01:03 → 01:08처럼 흔들렸고, 이 차이가 기사 변경 명세에 그대로 나타났습니다.

모든 목적 단계가 `OPTIMAL`로 끝난 경우에만, 각 목적값을 제약으로 고정한 채 `Σ|출발 − 원안 출발|`(배정된 원안 작업)을 최소화하는 다듬기 단계를 한 번 더 실행합니다. 남은 예산과 2초 중 짧은 시간만 쓰며, 목적 순서의 값이 하나라도 다르면 결과를 버립니다. 미처리·변경·이동 값과 최적성 판정은 바뀌지 않고, 실행 결과는 `solver_settings.departure_tie_break`(`optimal`/`feasible`/`not_found`/`skipped`)에 남깁니다. B2는 변경 수가 목적이 아니므로 같은 이동합계 안에서 변경 수가 줄 수 있습니다(오늘 저녁 예제 16 → 13건).

## 두 목적의 차이

| 방법 | 우선순위 |
|---|---|
| B2 | 전체 미처리 수 → 조정 가능 작업 이동합계 |
| B3 | 전체 미처리 수 → 변경 작업 합집합 크기 → 조정 가능 작업 이동합계 |

변경 작업은 원안 대비 차량 변경, 허용폭을 초과한 출발시각 변경, 같은 차량에 남은 쌍의 상대순서 역전 참여, 원안 미처리에서 신규 배정된 작업의 합집합입니다. 차량과 시각이 함께 바뀌어도 한 작업으로 셉니다. 역전의 상대가 고정 작업이면 그 고정 작업도 현행 지표 정의에 따라 역전 참여 집합에 들어갑니다. 작업 삭제로 순번만 당겨지는 경우는 변경이 아닙니다.

이동합계는 조정 작업으로 들어가는 접근+적재+지정 복귀입니다. 미래 고정 작업으로 들어가는 접근은 시간 제약에는 쓰지만 이동 목적에는 포함하지 않습니다. 결과의 실제 지표와 모형 목적값을 비교해 다르면 결과를 반환하지 않습니다.

## 시간 예산과 결과 상태

두 방법 모두 동일 입력으로 B1 초기안을 최대 1초 동안 구성합니다. 이 시간은 요청의 전체 예산에 포함되며, 남은 예산이 더 짧으면 그 시점에 중단합니다. 이후 모형 구성과 모든 최적화 단계도 남은 시간을 공유합니다. 이전 단계의 최적값이 증명된 때만 그 값을 고정하고 다음 목적을 실행합니다. 매 단계 총 예산을 새로 부여하지 않습니다.

초기안과 최적화 중 얻은 안은 해당 방법의 목적 순서로 비교해 더 좋은 유효 후보를 보존합니다. 솔버가 첫 해를 못 찾아도 유효한 초기안이 있으면 `FEASIBLE`입니다. 단, `objective_stages`는 실제 솔버의 `UNKNOWN/NOT_RUN`을 그대로 남겨 초기안을 최적해로 오인하지 않게 합니다. 유효 후보가 없으면 `UNKNOWN`, 입력이 부족하면 `INPUT_INCOMPLETE`입니다. 실제 입력 관계 오류는 `EngineInputError`로 반환합니다.

모든 단계가 최적이라고 증명되고 입력 부족이 없어야 `objective_proven=true`입니다. 미처리 목적의 최적값이 증명돼도 특정 미처리 작업 하나가 물리적으로 불가능하다는 뜻은 아닙니다. 작업별 원인은 직접 확인한 준비·장비·중량 하한 외에는 확정하지 않습니다.

`solver_version`, 요청/적용 시드, worker=1, 초기안 출처, 각 단계 목적값·하한·상태를 기록합니다. 최초 라이브러리 로딩은 예산에서 제외합니다. 입력 검증·최종 진단·운영체제 지연을 포함한 강제 프로세스 종료 보장은 없으므로 API 담당은 입력 크기·동시 계산·프로세스 시간 제한을 별도로 둬야 합니다.

## 남아 있는 제한

- 현행 계약은 고정 작업의 순서 정수도 보존합니다. 고정 순서 1 앞이나 빈 정수가 없는 고정 예약 사이에는 삽입할 수 없습니다. 따라서 최적성은 이 계약 모형 안의 결과이며 현장 전체 배차 공간의 최적성을 뜻하지 않습니다.
- 후보 접근 경로 누락은 보수적으로 입력 부족으로 표시합니다. 누락 구간을 0으로 가정하지 않으며 희소 행렬의 허용 범위는 후속 검토입니다.
- 입력 규모만으로 실행 시간을 보장하지 않습니다. [0.2.1의156회 실험](../../docs/experiments/engine-sensitivity-2026-11-08/README.md)과 [0.2.2의72회 후속 실험](../../docs/experiments/engine-profile-2026-11-08/README.md)은 규모·예산·조건에 따른 증명과 유효안의 차이를 기록합니다. 11월 7일 0.2.0의 원본 결과도 별도로 보존합니다.
- 반환 결과는 계속 `validation_status=not_run`, `approval_eligible=false`입니다. 엔진 내부의 모형 검사·지표 대조·테스트가 선효 담당의 독립 일정 검사기를 대신하지 않습니다.
