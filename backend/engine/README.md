# 최적화 엔진 첫 구현 · B0 / B1

담당: 황대겸. 개발 계약 v0.1.0을 읽는 독립 Python 모듈입니다. 웹·DB·외부 API를 호출하지 않고 입력을 변경하지 않습니다. 실제 앱 통합과 독립 일정 검사·승인은 별도입니다.

엔진 버전 `0.1.2-b0-b1`은 소수초 입력이 파싱 과정에서 잘려 분 경계로 통과하던 문제를 수정했습니다. 입력의 관측·수신·확인 시각에도 기존 v0.1 분 경계 규칙을 적용하며, 과거 실험 산출물은 당시 버전 기록으로 보존합니다.

## 실행

Python 3.12 환경에서 저장소 루트 기준:

```sh
python -m pip install -r backend/engine/requirements.txt
python -m backend.engine --snapshot "docs/development/v0.1/예제 데이터/01_snapshot.json" --output local/engine-results.json
python -m unittest discover -s tests/engine -v
```

`local/`은 Git에서 제외됩니다. 엔진은 저장소의 `docs/development/v0.1/공통 규격/contracts.schema.json`을 검증 기준으로 읽습니다. 패키지·컨테이너로 옮길 때 이 계약 파일도 포함해야 합니다.

```python
from backend.engine import EngineInputError, solve

result = solve(snapshot, "B1", {"seed": 0, "time_limit_seconds": 10})
```

반환값은 공통 계약의 `MethodResult`입니다. API 담당은 외부 `Results` 응답의 실행 ID·입력 해시·계획 버전을 서버에서 연결합니다. CLI의 `local-...` ID는 입력 해시 기반 로컬 표시이며 서버 실행 ID나 영속 저장 증거가 아닙니다.

## 구현 범위

- **B0:** 원안 배정·미처리를 유지하고 준비·시작/마감·중량·장비·근무·접근·복귀 조건을 진단합니다. 위반 배정을 삭제하지 않습니다.
- **B1:** 마감, 작업 ID 순으로 차량별 삽입 위치를 검사합니다. 삽입 뒤 그 차량의 전체 경로를 다시 계산합니다. 동률은 새 작업 도착시각 → 차량 ID → 삽입 위치로 정합니다.
- 미래 고정 예약과 출발 작업은 원안 그대로 보존합니다. 고정 작업에 새 마감 위험이 있어도 삭제하지 않습니다. 복귀/가용 미확정·모순 차량에는 신규 배정하지 않습니다.
- 마지막 출발 작업이 복귀한 장소와 차량 시작 장소가 다르면, 복귀 후 이동시간을 충족한 `available_at`인지 확인합니다. 경로가 없거나 시각이 모순이면 입력 부족으로 표시합니다. 장비·중량이 맞지 않는 차량의 불필요한 경로는 요구하지 않습니다.
- 변경 지표는 차량·허용폭 초과 출발시각·동일 차량에 남은 쌍의 역전 참여·신규 배정의 합집합입니다. 작업 삭제에 따른 행 번호 당김을 순서 변경으로 세지 않습니다.
- 모의 시나리오를 실제로 계산한 결과이므로 `computed`이지만, 실제 운송 데이터의 효과를 검증했다는 뜻은 아닙니다.

## 한계와 통합 시 주의

1. **B2/B3는 미구현입니다.** 해당 방법 호출은 `NotImplementedError`이며, B1 결과를 재사용해 최적해로 표시하지 않습니다. `objective_proven=false`, B1 상태는 `HEURISTIC`입니다.
2. **독립 일정 검사는 미구현입니다.** 모든 결과는 `validation_status=not_run`, `approval_eligible=false`입니다. 엔진 내부 진단과 테스트가 통합 담당의 독립 검사·승인 버전 확인을 대신하지 않습니다.
3. B1은 이미 삽입한 작업을 다른 차량으로 옮기며 전역 탐색하지 않습니다. 삽입 실패만으로 불가능을 증명하지 않으며 `SEARCH_LIMIT/not_proven`과 확인할 조건을 반환합니다. 준비+적재이동+여유가 마감보다 늦는 경우처럼 직접 확인되는 하한만 근거식으로 설명합니다.
4. 고정 작업의 `sequence` 정수 값까지 그대로 보존합니다. 고정 번호 사이에 빈 정수가 없으면 그 위치에는 삽입할 수 없습니다. 예를 들어 고정 `sequence=1` 앞에 새 작업을 넣을 수 없습니다. 이 제한은 시간상 불가능 증명이 아니며, 순서 식별 방식 변경은 API·DB 담당과 별도 합의가 필요합니다.
5. `EngineInputError`는 `.issues`와 `.category`(`invalid`/`incomplete`)를 가집니다. 입력 참조·중복·잠금 모순은 거절합니다. 확정되지 않은 변경 시간창도 계산에 적용하지 않습니다. API에서 입력 보류/검증 오류로 처리하고 정상 계산 완료로 표시하지 않습니다.
6. nullable 작업/차량 입력 때문에 일부 배정을 제외한 결과는 `INPUT_INCOMPLETE`로 표시합니다. 특히 **B0 이동경로가 없어 원안의 이동합계를 계산할 수 없는 경우**, v0.1 Metrics가 null을 허용하지 않아 `EngineInputError(category='incomplete')`를 반환합니다. 원안을 바꾸거나 0분을 만들지 않습니다. 입력 부족의 통일 응답은 후속 계약 검토 항목입니다.
7. 시간 예산은 후보 탐색 루프에서 확인하는 협조적 중단입니다. 입력 검사·마지막 진단까지 포함한 엄격한 프로세스 종료 시간이 아닙니다. 공개 시연 서버는 입력 크기·동시 계산·전체 실행시간을 별도로 제한해야 합니다. 엔진은 상주 프로세스를 만들지 않습니다.
8. 시드는 실행 기록에 남기지만 B0/B1은 무작위 탐색을 사용하지 않습니다. `seed_used=false`입니다. 입력 배열 순서에 의존하지 않는 동률 규칙을 사용하며, 시간 제한에 걸린 결과까지 완전 재현을 보장하지는 않습니다.

다음 작업은 B2/B3의 공정한 비교 조건과 초기해를 맞추고 사전식 목적의 단계별 상태·경계를 구현하는 것입니다. 배포는 모의 데이터 공개 시연을 먼저 준비하며, 이 모듈 자체를 공개 API로 실행하지 않습니다.
